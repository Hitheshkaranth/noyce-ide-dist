Command line, CI and team use

The noyce command line runs the IDE's analysis, coverage, coupling, trace and grading from a terminal or a CI job, writes the same records the IDE writes, and gates a pull request against a committed baseline run. Plus how a team shares .noyce/ through git.

The noyce command runs the same services the IDE panels run, bundled for Node. A record the CLI writes is the record the IDE writes for the same action, so opening the project in the IDE shows the CLI's results.

Install#

The CLI ships in the Noyce IDE source repository as packages/noyce-engine. From a checkout:

Terminal
npm ci
npm run engine:build                                  # bundles the engine for Node
node packages/noyce-engine/bin/noyce.mjs --help       # or: npx noyce --help, npm run noyce -- --help

Commands that analyse code (model, analyze, cover, verify, couple, grade) need the noyce-core sidecar binary. The CLI looks for it in this order and never builds it: NOYCE_CORE_BIN, services/noyce-core/target/release/noyce-core, services/noyce-core/target/debug/noyce-core, then packages/noyce-engine/vendor/noyce-core. If none is found it exits 3 and lists what it tried.

Commands#

Every command takes --project <path> (default: the current directory), --json (one JSON document on stdout, schema noyce.cli/1) and --out <dir> (where records go; default <project>/.noyce/).

Command Does what the IDE does at Writes
model Builds the program model. .noyce/analysis/model/
analyze [--timeout <s>] [--include-vendor] [--no-extras] [--no-codeql] MISRA Diagnostics → Scan: every installed analyzer plus the rule engine, then metrics and concurrency (skipped with --no-extras), then a CodeQL scan if CodeQL is installed (skipped with --no-codeql). .noyce/compliance/static-analysis.json, .noyce/analysis/{rules,metrics,concurrency}/, .noyce/codeql/
cover --host MC/DC Coverage: runs every tests/mcdc/*.c driver. .noyce/coverage/
cover --target <probe> --config <id> (--dumps <a.bin,b.bin> | --elf <f>) [--uninstrumented-elf <f>] [--chip <name>] Attaches to the probe through probe-rs and collects target coverage, from counter-RAM dumps you captured or, with only --elf, by halting the core and reading the counters. <probe> is a probe serial or identifier, or auto. Always detaches. Untested on hardware. .noyce/coverage/cov-probe-*.json
verify --target [--probe <serial|auto>] [--chip <name>] [--coupling] [--timing] [--run tests|duration] [--timeout <s>] [--duration <s>] [--statement] [--gcc-path <dir>] [--build-only | --reuse-image] Target verification → Build, flash & collect: detects the probe, builds the coverage-instrumented image with the portable build and your cross toolchain, flashes it, runs tests/target to their END line (or the application for --duration), halts, reads the counters and records them. Stops at the first step that fails and names it. Exit 3 when there is no probe or the target will not attach, flash or halt; 2 when the project cannot be built into an image; 1 when target tests fail, a run does not finish, or the counters do not belong to the flashed image. Unverified on hardware. .noyce/cov/build/target/, .noyce/coverage/cov-probe-target-target.json, .noyce/verification/target-verify/, .noyce/verification/target/
couple [--level <A-E>] Data & Control Coupling: analyze, measure and evaluate A-7(8). .noyce/coupling/, .noyce/verification/
trace Exports the traceability matrix. .noyce/do178c/traceability-matrix-<time>.csv
grade [--level <A-E>] Compliance Run → Take run. .noyce/compliance-runs/<run-id>/
gate [--baseline <run|path>] [--regressions-only] Compares the newest run with a baseline. CI only. nothing
kit … Builds, signs and verifies qualification kits. <out>/qualification/kits/
qualify --engine <id> | --all Runs the qualification corpus. <out>/qualification/<engine>/

Exit codes. 0 OK; 1 a gate or check failed; 2 usage or environment error (unknown command or flag, missing project, no runs to gate on, no software level); 3 a required tool is unavailable (no sidecar, no probe, no analyzer could run). An unknown flag is always exit 2; the CLI never runs a default in place of a mistyped flag.

The software level is never assumed. couple uses --level, else the level recorded in Compliance. grade uses the recorded level, and accepts --level only when no level is recorded or when it equals the recorded one. With neither, the command exits 2: "Choose and justify the project software level in Compliance (or pass --level) before taking a run. No level is assumed."

The gate#

noyce gate fails (exit 1) on:

  • regressions against the baseline: a claim that was satisfied and now is missing or failing, a producer that ran and now does not, or fewer objectives evidenced;
  • integrity problems: the run record fails its content hash, archived producer evidence is missing or altered, or the release inputs changed during or since the run;
  • readiness blockers: a producer ran and is unsatisfied, the working tree was dirty or unknown, no commit was recorded, or conformity-review items are open.

With --regressions-only, readiness blockers are reported as notes and do not fail the gate; regressions and integrity problems still do. Use it while a project is not yet certifiable, to gate on "nothing got worse".

The baseline is --baseline (a run id, or a path to a run directory or its run.json), else the run marked as baseline (Mark as reference run in Compliance Run), else the run before the newest.

Terminal
$ noyce grade --project fw --level C
$ noyce gate --project fw --baseline run-20261103-170210 --regressions-only

What the CLI does not do#

  • Target coverage collection is untested on hardware.
  • Anything that needs a person (dialogs, AI agents, document authoring, signing a review) is refused with a reason.

CI#

templates/ci/ in the source repository holds a pipeline script and templates for GitHub Actions and GitLab CI:

File Copy to, in your firmware project
templates/ci/noyce-ci.sh .noyce/tools/noyce-ci.sh
templates/ci/github/noyce-compliance.yml .github/workflows/
templates/ci/github/noyce-target-coverage.yml .github/workflows/ (self-hosted runner with a probe)
templates/ci/gitlab/noyce-compliance.gitlab-ci.yml include it from .gitlab-ci.yml

noyce-ci.sh looks for clang, llvm-cov, arm-none-eabi-gcc, cppcheck and cbmc and records what it found in toolchains.json, then runs model, analyze, cover, couple, grade and gate --baseline. It writes each step's JSON and log, summary.md and junit.xml to .noyce/tmp/ci/, and copies the graded run there for upload.

Variable Default Meaning
NOYCE noyce How to run the CLI, for example node /opt/noyce/packages/noyce-engine/bin/noyce.mjs.
NOYCE_PROJECT . Project root.
NOYCE_BASELINE content of .noyce/ci-baseline Baseline run id or path. Required.
NOYCE_COVER host host or target.
NOYCE_PROBE none Probe selector for target mode. With only this set, the step is noyce verify --target --probe <sel>: build, flash, run, collect.
NOYCE_GCC_PATH none Cross toolchain bin directory for the instrumented build (optional).
NOYCE_VERIFY_COUPLING, NOYCE_VERIFY_TIMING none 1 adds --coupling / --timing (optional).
NOYCE_COVER_CONFIG none Collect-only: the instrumented build id; required with dumps or an ELF.
NOYCE_COVER_DUMPS none Collect-only: comma-separated counter-RAM dumps from a run done outside the job.
NOYCE_COVER_ELF none Collect-only: instrumented ELF; without dumps the CLI reads the counters live.
NOYCE_COVER_UNINSTRUMENTED_ELF none Plain build, to measure probe overhead (optional).
NOYCE_CHIP none probe-rs chip name when it cannot be auto-detected (optional).
NOYCE_REQUIRED_TOOLS none Tools whose absence fails the job before any step runs.
NOYCE_CI_OUT .noyce/tmp/ci Where outputs go.
NOYCE_CI_LLVM_DIRS Homebrew LLVM prefixes Extra directories searched for LLVM tools.

The job's exit code follows the CLI: 1 means a regression against the baseline; 2 a setup problem (no baseline, CLI not runnable, a target run with no probe); 3 a missing tool. A regression wins over an environment problem, and the environment annotations stay in the log.

Baseline. Commit the run you accept under .noyce/compliance-runs/<run>/ and write its id to .noyce/ci-baseline. Re-baselining is then a reviewable commit.

Signing. The pipeline never signs anything and never passes a key to the CLI. If NOYCE_SIGNING_KEY or NOYCE_QUALIFICATION_KEY is set in the job, it warns and still does not use it.

Limitation

With NOYCE_COVER=target and no NOYCE_PROBE, the step stops with exit 2. In collect-only mode (NOYCE_COVER_DUMPS or NOYCE_COVER_ELF set) a missing NOYCE_COVER_CONFIG stops it with exit 2 and an annotation naming what is missing; cover is not run. A runner with no probe plugged in makes verify exit 3 (tool unavailable), never a regression.

Team use without a server#

A team shares .noyce/ through git, like the code. No server is involved.

One file per record. These stores keep each record in its own file, so two people adding records on two branches never conflict:

Store Directory under .noyce/
Review records process/reviews/
Problem reports process/problem-reports/
MISRA deviations process/deviations/
Roster process/roster/
Coverage classifications process/coverage-classifications/
Annex A verifications and overrides process/annex-a-verification/
Trace links and their suspect-link reviews requirements/trace-links/
  • Adding a record adds a file. Editing a record rewrites only its file, so two branches conflict only when they make different decisions on the same record, which a person should resolve.
  • Append-only records (reviews, coverage classifications) are named by id plus a digest of their content, and are never rewritten.
  • Removing an editable record writes a tombstone instead of deleting the file.
  • An older single-file store (process/review-records.jsonl and the like) is still read, and is split into one file per record the first time the IDE writes to it. Upgrade the whole team together: an older IDE build still writes the old single file.

The audit ledger is one hash chain, so it merges with a git merge driver instead. Set it up once per project, then once per clone:

Terminal
bash <noyce>/templates/team/install-team-git.sh       # once per project; commit the results
git config merge.noyce-ledger.name   "Noyce audit ledger merge"
git config merge.noyce-ledger.driver "node .noyce/tools/noyce-ledger-merge.mjs %O %A %B %P"

The driver verifies both sides and refuses to merge a ledger that does not verify. It keeps every entry from both sides, orders new entries by time, re-chains them after the shared prefix and appends a ledger.merged entry recording each moved entry's old and new position, so an old signature citation still resolves.

What to commit. Everything under .noyce/ except caches and scratch. The IDE writes .noyce/.gitignore listing build trees (build/, cov/build/, tests/build/, timing/build/), the program model (analysis/model/), tmp/, CodeQL databases, the search index and downloaded manuals. Never ignore the whole of .noyce/: that hides the evidence from configuration control.

Limitations#

  • These instructions run the CLI from a Noyce IDE source checkout; kit and qualify need one, because the corpora and kit builder live there.
  • Target verification in CI needs a self-hosted runner with a probe and the cross toolchain, and is unverified on hardware.
  • A central record server is not part of Noyce IDE; teams share records through git.
