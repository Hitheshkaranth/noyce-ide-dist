Import and build a TI or ST project

Two end-to-end walkthroughs, a TivaWare project from Code Composer Studio and an STM32CubeIDE project, from the import wizard to a recorded build, its memory map and its pin configuration.

Two real projects, imported into a fresh copy and taken as far as this computer allows. Every step and screenshot below was checked in the IDE:

  • a TI Tiva TM4C1294 project from Code Composer Studio;
  • an STM32G431 project from STM32CubeIDE.

The two take different routes after the import. Here, the TI project built and linked. The STM32 project was blocked by the toolchain, and the IDE said exactly why. Both outcomes are shown.

Before you begin#

For You need
Importing either kind Nothing beyond Noyce IDE. The reference-manual download needs a network connection.
Building a TI project The TI ARM compiler (armcl, TI Arm Clang or GNU Arm), and TivaWare when the project uses it. Noyce IDE finds them on your PATH or under ~/ti, /Applications/ti, C:\ti or %USERPROFILE%\ti. See Build.
Building an STM32 project make and a complete Arm GNU Toolchain, that is arm-none-eabi-gcc with its C library (newlib). STM32CubeIDE's bundled toolchain or the Arm GNU Toolchain both work.
Flashing and debugging an STM32 arm-none-eabi-gdb, plus OpenOCD, STM32CubeProgrammer or st-util.

Tip

Try this on a copy of your project first. The import itself writes only .noyce/, but the STM32 workspace step (step 3 of the STM32 walkthrough) writes .vscode/ files and overwrites files of the same names.

The import wizard#

On the Noyce IDE start tab, select Import project….

Selecting a type opens the matching picker:

Type Pick
Code Composer Studio The project folder, the one holding .ccsproject and .cproject.
STM32CubeIDE The .ioc file. Cancel that picker to choose the project folder instead.
MPLAB X IDE, Generic Folder The project folder.

What happens next:

  1. The wizard reads the project and shows what it found, for example TI Code Composer Studio Project Detected.
  2. The window reloads with the project open. When you open a folder for the first time, Code-OSS asks Do you trust the authors of the files in this folder?. Choose Yes, I trust the authors; in Restricted Mode, Code-OSS does not run tasks, so the builds below would not start.
  3. A Project Imported notification appears.
  4. Noyce IDE detects the microcontroller from the project's files and fetches its reference manual for Register Knowledge. A notification reports the outcome:
    • Reference manual indexed: the PDF is in .noyce/manuals/ and its register index in .noyce/knowledge/.
    • Reference manual for the part, as a warning: the download failed. The message names the manual and its URL, so you can download it in a browser and choose it with Choose PDF… in Register Knowledge. A server that does not answer is abandoned after 30 seconds.
  5. The project is added to Recent projects on the start tab, marked Current.

The import writes only the .noyce/ folder, including its .gitignore for caches and the downloaded manuals. See The .noyce folder.

Walkthrough: a TivaWare project from Code Composer Studio#

The project: an MPDU controller on a TM4C1294NCPDT, built with TI ARM CGT 20.2.6.LTS and TivaWare 2.2.0.295, both installed under ~/ti.

1. Import it#

Import project… → Code Composer Studio → the project folder. After the reload and the trust prompt, the reference-manual notification reports that the TM4C1294 datasheet (spms433.pdf) was downloaded and indexed.

2. Build#

The status bar now shows the configuration (Debug) and Build. Press ⇧⌘B (CtrlShiftB on Windows).

The build runs as the Noyce: Build Debug task in the terminal. When it finishes, the status bar reads Built 12.7s, and its warnings are in the Problems panel. The objects, .out and .map are written to .noyce/build/ccs-Debug/, not to the project's own Debug/ folder.

3. Read the result in the Build view#

Open the Build Pipeline tile, or ⌘⌥N then B.

The header names the compiler that was found and its version. Image size comes from the link map. Diagnostics lists each warning with its TI code (994-D, 179-D…); select a file and line to open it. See The Build view for the other tabs.

4. See where the memory goes#

Select Open Firmware Memory.

Firmware Memory finds the map the build wrote and shows each memory region against its size, with its sections and the cost of each object file. On this project, SRAM is 106.0 KB of 256 KB and FLASH is 54.6 KB of 1 MB. Worst case stack depth stays —: it needs GCC -fstack-usage records, which a TI build does not produce. The configured .stack size (2.0 KB) is still shown.

5. Rebuild the pin map from the source#

A CCS project has no .ioc, so the pin configuration is reconstructed from the TivaWare calls in the C source (GPIOPinConfigure, GPIOPinType…, SysCtlPeripheralEnable). To run it and open the result, use Noyce Tiva: Import Pin Config from Source from the Command Palette. In the folder picker, choose the project folder (the open folder is preselected).

The Pin Configurator opens on the part and package detected from the source. The peripherals the source configures are switched on, and each pin is coloured by its use. Generate init code writes initialisation code for the configuration shown. See Pin Configurator.

Walkthrough: an STM32CubeIDE project#

The project: an H-bridge controller on an STM32G431VBTx, last built in STM32CubeIDE on a Windows machine.

1. Import it#

Import project… → STM32CubeIDE → the project's .ioc file. After the reload and the trust prompt:

  • the .ioc opens in the Pin Configurator, with the part, the package and the peripherals the .ioc enables;
  • the reference manual (RM0440 for the STM32G4) is fetched. In the run shown here, st.com did not answer, so the warning gave the manual's URL to download by hand.

2. Check the toolchain#

Run Noyce STM32: Validate Toolchain. The Noyce STM32 output lists each tool, then whether you can build, flash and debug, and why not.

On the computer used here, all three were blocked:

  • Build: Homebrew's arm-none-eabi-gcc formula has no C library (nano.specs and libc.a are missing). Fix it by installing the Arm GNU Toolchain (brew install --cask gcc-arm-embedded) or STM32CubeIDE, then putting it first on your PATH or setting noyce.stm32.armToolchainPath.
  • Flash: no STM32CubeProgrammer, OpenOCD or st-util, so no flash task is generated.
  • Debug: no arm-none-eabi-gdb and no GDB server.

3. Set up the workspace#

Run Noyce STM32: Regenerate Workspace Files. It writes .vscode/tasks.json, launch.json, settings.json, extensions.json and compile_commands.json for the open folder:

  • a make build task, STM32 Build (Debug), which becomes the ⇧⌘B build;
  • a flash task, when a flash tool was found;
  • a Cortex-Debug launch configuration;
  • clangd set up for the project.

Noyce STM32: Import CubeIDE Project does the same after asking for the .ioc or project folder.

4. Build#

The build depends on the makefiles STM32CubeIDE generated in Debug/. Those makefiles hold absolute paths from the computer that generated them.

With ⇧⌘B. The task runs make -j4 all in Debug/. Here, the makefiles named C:/… paths, so make stopped with makefile:63: *** multiple target patterns. Stop. The task's description in tasks.json warns about this when it is generated. The build is still recorded in Build Status, with the compiler version.

From the Build view. The view checks the makefiles before running them. Because they name paths that do not exist on this computer, Build is disabled and Build blocked names one such path. It gives two ways out:

  • Regenerate the makefiles: run the STM32 CubeIDE Headless Build task (it needs STM32CubeIDE installed), or build once in STM32CubeIDE on this computer.
  • Build with a generated makefile: Noyce IDE writes its own makefile from the .cproject and .ioc, under .noyce/build/stm32-<configuration>/portable-build/, and builds with arm-none-eabi-gcc and make. This is not the CubeIDE build, so check its output against a CubeIDE build before you rely on it.

Here, the generated-makefile build failed in 0.2 s, because this compiler has no newlib. The Output tab begins with a one-line hint saying so. Errors reads 0 with Failed before any located error; see Output: the compiler stopped before it reported any error against a file and line. With a complete toolchain, the same button compiles the project, and the link map feeds Firmware Memory as in the TI walkthrough.

5. Find the builds again#

Every recorded build is listed in Build Status in the Noyce IDE sidebar, newest first. Hover a build to see what ran (CubeIDE makefile, Generated makefile or CubeIDE headless) and its toolchain. Select it to open the Build view.
