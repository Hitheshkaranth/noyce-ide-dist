Program model and provenance

The program model is one clang-parsed description of your C code that the rule engine, metrics, flowgraphs, coupling, unit test generation and timing all read. Provenance says how each result was produced, and decides whether it may close a DO-178C objective.

The program model#

Noyce IDE parses your C and C++ sources once with clang and keeps the result as the program model: for each function, its signature, attributes, control-flow graph, decisions and conditions, reads and writes of globals, calls and tokens, plus a linkage table across translation units. The flowgraph and metrics, Timing & Stack and Unit Tests read it, and the interrupt analysis builds it when it runs. The MISRA rule engine builds its own copy on every scan.

Build it#

There is no separate view for the model. It is built from the surfaces that need it:

  • Flowgraph & Cross-Reference → Compute metrics always rebuilds the model, then computes metrics.
  • Timing & Stack → Build program model, which shows progress and can be cancelled.
  • Unit Tests → Build program model, shown when there is no model yet.
  • Quality Trend → Capture Snapshot.
  • From a terminal, noyce model (see CLI).

A build runs as a background job with a 15-minute limit. If it times out or you cancel it, the previous model is kept unchanged.

What it needs#

  • clang on PATH, or set NOYCE_CLANG. clang is used only as a parser; your own compiler still builds the firmware. No minimum version is enforced; the version used is recorded in the model.
  • For Arm targets, the Arm GNU Toolchain (which includes newlib) for the C library headers. Noyce IDE looks in the usual install locations, including STM32CubeIDE and TI CCS; set NOYCE_ARM_TOOLCHAIN if yours is elsewhere. A translation unit that cannot find its C library headers is left out of the model, and the build summary says so.

Where the compile flags come from#

  1. A compile_commands.json in the project (at the root, in build/, Debug/, Release/, or up to two levels down). If it has no -D defines, defines derived from the project configuration are added.
  2. Otherwise, the source lists in Eclipse-generated makefiles (Debug/, Release/, build/) and a root Makefile. Make is never run.
  3. Otherwise, a scan of the project's source files, with the include paths and defines read from the project configuration.

Only flags that affect parsing are kept (target, -D, -U, -I, -include, -std, -mcpu and similar); the rest are counted as dropped.

Compiler dialects. A header that maps vendor keywords to attributes clang accepts is force-included, chosen from the compiler and project files: TI (armcl, CCS projects), IAR (iccarm, .ewp), Keil (armcc, armclang, .uvproj) or GCC. Two vendor features cannot be mapped this way, and the model records it: IAR @ placement, and TI #pragma DATA_SECTION / CODE_SECTION.

Where it is stored#

Path under .noyce/ Holds
analysis/compile_commands.json, analysis/build.json The compile commands used, where they came from, and the build hash.
analysis/model/index.json The index: clang version, dialects, target, limitations, translation units, linkage, call graph.
analysis/model/<hash>.json One file per translation unit.
analysis/dialects/*.h The dialect headers.

The model is regenerated from source, so .noyce/.gitignore excludes analysis/model/.

Provenance#

Every result Noyce IDE records carries a provenance tag saying how it was produced, shown as a badge next to the result:

Badge Meaning May close an objective?
Measured Produced by executing or instrumenting the real build: coverage counters, traces, test verdicts. Yes.
Derived Computed deterministically by an analysis tool from the code. Yes.
Heuristic Regex, name matching or model output. Advisory only. Never.
Declared A human statement: a justification, deviation or review. Only when signed by a person on the project roster.

Hover a badge for the producer, the environment (for example "Measured · host, stubbed") and, for a declared record, who signed it and whether they are on the roster. A heuristic badge also says "Advisory — cannot close an objective."

Grading enforces it. When the Annex A objectives are graded, evidence that is heuristic, untagged, or declared without a rostered signer is set aside as advisory before anything is counted. It is listed beside its objective but cannot make it satisfied, partial or failing.

Note

The MISRA rule engine's findings are tagged derived, but the rule engine's runs are not yet used as evidence for objectives: A-5 coding-standard evidence still comes from cppcheck. See MISRA rule engine.

Limitations#

  • clang must be installed; there is no bundled parser.
  • Without the Arm GNU Toolchain's newlib headers, affected translation units are missing from the model.
  • IAR @ placement and TI section pragmas are not modelled.
  • C++ translation units (.cpp, .cc, .cxx, .C, -x c++ or a g++ / clang++ driver) are modelled with their functions and methods under qualified names (ns::Class::method), plus classes, bases, virtual members, namespaces, templates and using-directives. Templates are modelled as written, once, not per instantiation. Functions containing try/catch, throw or range-based for have no control-flow graph (cfg: null), and the model index lists this under its limitations.
  • Building the model from the interrupt analysis shows no progress and cannot be cancelled. Progress is also not reported when the build runs on a single worker (3 cores or fewer, or NOYCE_MODEL_JOBS=1).
