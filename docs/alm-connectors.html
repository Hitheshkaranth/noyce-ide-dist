ALM connectors

Connect Noyce IDE to IBM DOORS Next, Siemens Polarion or Jama Connect to pull system requirements and push trace links back.

Noyce IDE can read system requirements straight from IBM DOORS Next, Siemens Polarion or Jama Connect, and write its trace links back to them as links. The pulled requirements go into the same system register as a ReqIF or CSV import. Suspect links and change impact work on them the same way.

Warning

The three connectors were built from each vendor's public API documentation. They are tested against mock servers that replay the documented requests and responses, but not yet against a live server. The view marks each one Not verified against a live server. Check your first pull and your first push by hand. If a connector does not work with your server, exchange a ReqIF file instead.

What each connector does#

Server Protocol Pull Push (both ends on the server) Push (Noyce-only requirement) Authentication
IBM DOORS Next OSLC RM 2.0 (RDF/XML) Requirements from the project area's query capability, paged Link property on the system requirement (default oslc_rm:satisfiedBy) The same link property, pointing at the Noyce requirement's URI User name and password, or a bearer token
Siemens Polarion REST API v1 (JSON:API) Work items of the project, optionally filtered by type and Lucene query, paged Linked work item from the refining item to the system requirement (default role relates_to) Linked OSLC resource on the system requirement Personal access token
Jama Connect REST API v1 Items of the project, optionally of one item type, paged; pick-list values resolved to their names Relationship from the system requirement to the downstream item URL link on the system requirement OAuth client credentials, or user name and password

Every connector pulls typed attributes: DOORS Next custom attributes, Polarion fields and Jama fields (labelled by the item type's own field definitions). Bookkeeping fields such as created and modified dates and authors are left out. A change to a requirement's text or to one of its attributes makes its trace links suspect. Fetching the same requirement again does not.

Push writes links only. It never changes a requirement's text or fields. A link already on the server is not written a second time, so pushing twice is safe.

Set up a connection#

  1. In Requirements & Evidence, open the ALM connectors tab, or pick the server from the ALM connectors menu in the header.
  2. Choose the server and fill in Server URL and Project:
    • DOORS Next: the RM application URL, such as https://jazz.example.com:9443/rm, and the project area's title.
    • Polarion: the server root, such as https://polarion.example.com, and the project id.
    • Jama Connect: the server root, such as https://example.jamacloud.com, and the project id (the number in the project's URL).
  3. Choose the authentication, enter the user name or client id, enter the secret, and select Save next to it.
  4. Open Field mapping if you need it: item type, query, which field holds the id or text, the link role written back, and which attributes to keep.
  5. Select Save settings.

The settings are kept in .noyce/requirements/alm/connections.json and can be committed with the project. The secret is not. It goes to the IDE's secret storage on your machine, keyed by connector and server, and the view only shows whether one is stored. Forget removes it.

Note

The view cannot reach the server itself. Every request goes through the IDE, which adds the stored credential. The IDE only sends requests to the server you configured and does not follow redirects to another server.

Test connection#

Test connection checks each step of reaching your requirements and stops at the first one that fails. It shows the HTTP status, the URL and the server's own message, for example:

  • Credential: no credential is stored for this server.
  • Root services (DOORS Next): HTTP 401, the server rejected the credential.
  • Project area (DOORS Next): no project area has that title. The project areas your account can see are listed.
  • Project (Polarion, Jama): HTTP 404, project not found; or HTTP 403, your account has no permission for it.
  • Item type (Jama): the item type id does not exist.
  • Read requirements: how many requirements the query returns.

For Jama with OAuth, a wrong client id or secret is reported as a failed token request, not as a project error.

Pull requirements#

Pull requirements reads every requirement the project and mapping select and imports it into the system register, under System requirements (imported). Each requirement keeps where it came from: the connector, server, project, the server's item id, its revision, and when it was fetched. Hover the source column to see them.

Pulling again replaces what the previous pull from that project brought in. Trace links are checked before and after the pull, so a requirement that changed on the server shows up under Suspect links with the old and new text side by side. The pull is recorded in the audit trail with a hash of what was pulled. The last pull is kept in .noyce/requirements/alm/<connector>-pulled.json; push uses it to find each requirement on the server.

If the server limits how fast you can send requests, the connector waits as long as the server asks and tries again, up to four times.

Push trace links#

Push trace links writes each of the project's trace links back to the server:

  • When both ends of a link are on the server (for example an HLR kept in Polarion that refines a system requirement), it writes the server's own link: a Polarion linked work item, a Jama relationship, or a DOORS Next link property between the two requirements.
  • When the refining requirement exists only in Noyce, it writes a link from the system requirement to that requirement's URI. The URI is urn:noyce:requirement:<id> unless you set Noyce requirement URI base, for example to a web page that shows your requirements.

A link to a requirement that was not pulled from this server is skipped and listed with the reason. The push is recorded in the audit trail.

Limitations#

Limitation

  • None of the connectors has been run against a live server yet.
  • DOORS Next form-based login (j_security_check) and OpenID Connect are not supported. Use basic authentication or a bearer token your server accepts, or exchange ReqIF files.
  • Self-signed server certificates are not accepted unless your operating system trusts them.
  • Polarion enumeration values are recorded by their ids, not their display names.
  • DOORS Next custom attributes are named by the last part of their property URI unless you map them under Attributes to keep.
  • Classic DOORS (9.x) has no connector. Exchange ReqIF files with it.
