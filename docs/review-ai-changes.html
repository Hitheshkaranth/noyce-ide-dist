Review and apply AI changes

How a fix proposed by Fix with Noyce, the CBMC or CodeQL fixers, or an Orchestrator agent becomes an approved, gated change set before it touches your code.

Code changes proposed by AI in Noyce IDE are never written straight into your source. They arrive as a change set: the proposed files, held next to the project, that have to cite an authority, pass gates and be approved by a named person before they are applied.

This applies to Fix with Noyce in MISRA Diagnostics, the fixers in Formal Verification and Code Scanning, the Firmware Validation Loop, and code written by Orchestrator agents.

The point of the path is that the code an auditor sees can always be traced back to a reason (the authority), a check (the gates) and a person (the approver). An AI wrote the draft; none of those three steps are the AI's.

1. Propose a fix#

In MISRA Diagnostics, select a finding, then Fix with Noyce. The dialog shows Generating a grounded fix… while the model works.

What happens before you see a diff:

  1. Fact check. The model is first asked whether the finding is a real violation. A disputed finding cannot be staged, and the dialog says why.
  2. A bounded rewrite. The model rewrites only a window around the finding: the enclosing function when it is short, otherwise about 25 lines either side. The rest of the file is kept byte for byte, so a fix cannot silently change code far from the finding.
  3. Safety checks on the result. If the proposal changes nothing, or would damage the file, staging is disabled and the dialog says so.

When the proposal is a real change, the dialog shows its line diff: each changed line with three lines around it, and the unchanged stretches of the file folded. Select a folded row to show those lines. Select Stage change set to keep the proposal, Discard to drop it, or Raise problem report from finding to track the issue instead. Fix All stages one change set for every auto-fixable finding.

A proposal can be well-formed and still wrong. Read the diff against the code it changes, not against the explanation.

Tip

Pick the model for fixes in the Fixer model select at the top of MISRA Diagnostics. It overrides the global model for fixes only.

2. Open the change set#

Open Evidence Records → Change sets. Each staged set shows its files with a per-file diff.

3. Cite the authority#

Every change needs a reason that a reviewer can trace. In Authority, enter the problem report, change request or CCB decision the change answers, and select Cite. If none exists yet, Raise problem report from finding creates one.

4. Run the gates#

Select Run gates. All five gates always run, so you see every problem at once:

Gate Passes when
Integrity The changed files have no structural damage a compiler would reject, such as an unbalanced brace or a stray byte-order mark. Problems already in the original file are listed but do not fail the gate.
Authority The cited problem report is open or in work, or a CCB decision taken with quorum approved the change.
Build The project builds with the change.
Unit tests The project's tests pass with the change. If they also fail without it, the result says so.
MISRA The change introduces no new MISRA findings.

A gate that cannot run is marked skipped, never passed: for example when the project has no portable build, no unit tests the IDE can run, or no C or C++ file in the change. Gating refuses to start if the staged content was edited outside the change set.

5. Approve and apply#

Choose the Approver from the roster and select Approve. Then select Apply.

Apply writes all of the files or none of them. If any file was edited after the gates ran, the change set is marked stale and nothing is written; propose the fix again on the current code. If a write fails part-way, the files already written are restored.

To decline a change, enter a reason and select Reject; a rejection always records its reason. Every step (creation, cited authority, gate results, approval, rejection, apply) is kept in the change set's history.

Orchestrator agents#

Code from the Orchestrator's coding agents goes through the same path. With Auto-apply agent code off, the agent output tab shows Proposed file changes with Stage all as change set. With it on, the change set is staged for you automatically. In both cases nothing is written until you approve and apply it here.
