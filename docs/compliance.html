Compliance & certification

The Compliance Dashboard, Annex A objectives, compliance runs, certification readiness, evidence records, the audit trail and the certification package.

For the order to use these in, follow the DO-178C walkthrough. This page describes each surface.

Compliance Dashboard#

The project's standing against a certification framework, objective by objective. Open it from the Compliance tile or ⌘⌥N then C.

Header. Choose the framework (DO-178C, ISO 26262, IEC 62304 or IEC 61508) and the assurance level. The buttons along the top:

Button Does
Generate with AI Has your model draft the evidence for open objectives. Disabled until there are requirements.
Generate via Orchestrator Puts each open objective on the Orchestrator board as a card.
Generate All Evidence Runs every evidence producer the dashboard knows.
Scan Rescans the project (⌘S inside the dashboard).
Analysis Tools, Coupling, MC/DC Coverage Open those surfaces.
Evidence Pack Writes a printable HTML evidence pack.
Certification Package Writes the sealed package (below).
JSON Exports the dashboard as JSON (⌘E).

Body. Counters for requirements linked, design allocation, verification and analysis findings; the certification article with satisfied, partial, open and N/A counts; structural coverage against DO-178C A-7; and the objectives table, grouped by Annex A table, with each objective's reference, independence, status and the output it needs.

Select an objective to open its drawer: the evidence behind it, Generate … with … for the agent that can produce it, its tool, and Review proposed evidence, where a reviewer from the roster accepts or rejects the evidence with a note.

Note

Set the assurance level here. The level in Settings has no effect. See Known limitations.

How an objective is graded#

The grading is deliberately strict, so a green objective means the same thing to you and to an auditor:

  • Only the objective's own evidence counts. A coverage objective reads coverage results, a review objective reads review records. A good number elsewhere in the project does not leak in.
  • Proxies cap at partial. A project-wide measure, such as overall test coverage, can show progress but cannot satisfy a specific objective.
  • A person closes it. The final step is always a review record by someone on the roster. Whether that review counts as independent is worked out from who wrote the item and who reviewed it.
  • "Open" is not "failed". An objective with nothing mapped yet is open. It only shows as failing when a check mapped to it actually failed.

Licensed Annex A table#

Expand Licensed Annex A table to import the applicability, independence and control category of each objective from your licensed copy of DO-178C. Write blank template creates the file to fill in. Until the table is imported, the PSAC, SVP, SCMP, SQAP and SAS stay marked DRAFT.

Compliance Run#

A reproducible measurement of the whole project at one commit. Open it from the Compliance Run tile or Noyce Compliance: Take a Compliance Run.

  • Take a run runs every evidence producer (static analysis, code scanning, formal verification, structural coverage and the rest) against the current configuration and stores the result under .noyce/compliance-runs/.
  • Mark baseline fixes a run as the reference later runs are compared with.
  • Annex A overlay sets up the objective map and objective text files.
  • Objective map shows which producer discharges which objective. Map… assigns one; a mapping always records its basis.

Each run shows its configuration, objectives by table, what each tool reported, conformity checks, the change since the previous run, and every run on record. A run cannot be exported when a producer failed, sample data was used, there is no commit, or the working tree has uncommitted changes.

Certification Readiness#

Release blockers, weak evidence and next actions in one queue. Open it from the Readiness tile.

Evidence that came from sample data is labelled inadmissible and never counts.

Warning

In v2.0.7 the Security dimension reads "0 CodeQL alert(s)" even when CodeQL has never run. Check Code Scanning for whether a scan exists before reading that zero as a result.

Evidence Records#

The project's process records. Open it from the Evidence Records tile.

Tab Holds
Verification cases Test cases and their results.
Problem reports Defects and change requests that authorise changes.
CCB Change control board meetings, quorum and decisions.
Change sets Proposed code changes awaiting gates and approval. See Review AI changes.
MISRA deviations Approved deviations from MISRA rules.
Reviews Review records with checklists. Independence is worked out from who wrote and who reviewed the item.
SQA / CM / liaison Quality assurance, configuration management and certification liaison records.
Roster The people who may review, approve and sign. Add everyone here first.
Tool qualification The tools used and their qualification status.
Parameter data Parameter data items.

Audit Trail#

Every significant action, recorded in a hash chain. Open it from the Audit Trail tile or Noyce Team: Open Audit Log.

Each entry's hash covers its sequence number, time, actor, action and the previous entry's hash, so editing or removing any entry breaks the chain and the check reports where. The ledger is stored in .noyce/audit-ledger.json.

Certification Package#

Select Certification Package on the Compliance Dashboard. Noyce IDE runs CBMC and CodeQL, then writes one package to .noyce/certification/ as Markdown, HTML and JSON, with these sections: metadata, executive summary, objectives, Annex A coverage, compliance run identity, life-cycle data, requirements and traceability, MISRA, CBMC, CodeQL, review records, and the audit trail.

The button is disabled until there are requirements and every objective has been assessed or reviewed, and the export is refused while the document set has unwaived contradictions.

Note

The package is sealed with SHA-256 hashes anchored to the audit trail, so later changes are detectable. It is not signed with a private key.

Other compliance surfaces#

  • Cyber Assurance, Data & Control Coupling, Object Code Traceability, MC/DC Coverage and Quality Trend are described in Analysis & proof.
  • Review Workflow shows a requirement's linked evidence and its required sign-offs.
