Analysis & proof

Static analysis, formal verification, code scanning, measured MC/DC coverage, coupling, object-code traceability, tests, cyber assurance and code-quality trends, and what each needs installed.

Every surface on this page measures your code with a real tool. When the tool is not installed or has not been run, the surface says so; it never shows sample results as yours. Install what you need from Optional tools.

Surface Tool DO-178C
MISRA Diagnostics cppcheck (MISRA addon) or clang-tidy A-5
Formal Verification CBMC 6.9.0 A-5, A-6 (analysis, not tests)
Code Scanning CodeQL 2.25.6 A-5
MC/DC Coverage LLVM/Clang 18+ A-7
Data & Control Coupling Project graph A-7(8)
Object Code Traceability arm-none-eabi-objdump A-7(9)

MISRA Diagnostics#

Coding-standard findings from every analyzer, in one list. Open it from the tile or Noyce Compliance: Open MISRA Diagnostics.

How to use it

  1. Select Scan. Noyce IDE runs cppcheck with the MISRA addon, or clang-tidy, and falls back to a built-in heuristic scan only when neither is installed.
  2. Filter by Severity (Mandatory, Required, Advisory) or by Tool.
  3. Select a finding to see its rule, its file and line, and the tool that reported it. Open in Editor jumps to the line.
  4. Fix with Noyce proposes a fix as a change set; see Review AI changes. To accept a finding instead, record a deviation in Evidence Records → MISRA deviations.
  5. Export Findings saves the list.

The counts line is worth reading. On the Canister copy it says that 624 of 1,532 findings were stored, because the run stores at most 500 coding-standard findings per analyzer; no defect-class finding is ever dropped.

Important

Heuristic findings are marked not evidence and never count toward an objective. Install cppcheck for findings an auditor will accept.

Formal Verification (CBMC)#

Bounded model checking proves array bounds, arithmetic overflow and your assertions, or produces a counterexample. Open it from the CBMC Verification tile or Noyce Compliance: Open Formal Verification.

  1. Install CBMC with Install CBMC in the view, or brew install cbmc.
  2. Select Generate harnesses to write one harness per code unit from your accepted low-level requirements: inputs bounded by each LLR's stated ranges, called functions stubbed from their prototypes, and the LLR's properties asserted. Harnesses are written to cbmc-harness/llr/ as a change set, so you approve them like any other code.
  3. Select Run Verification (or Run harnesses). Each property is reported as proved or failed with its trace.

CBMC results are analysis: they support code review and never count as tests. A failed property can be sent to Fix with Noyce or turned into a problem report.

Code Scanning (CodeQL)#

A semantic security scan that follows data from inputs through your code. Open it from the tile or Noyce Compliance: Open Code Scanning (CodeQL).

  1. Select Install CodeQL if it is not installed. Noyce IDE downloads the official CodeQL bundle and checks its SHA-256.
  2. Choose the query pack: security-extended or security-and-quality.
  3. Select Run scan. For TI Code Composer Studio projects the scan uses the include paths from the project's .cproject.

How the code is extracted. CodeQL normally watches the project's build to see every file exactly as compiled. Its tracer cannot follow the TI armcl compiler, so a traced scan of a TI project extracts nothing. Noyce IDE then repeats the scan with --build-mode=none, which reads the sources directly and guesses include paths and defines. On the Canister firmware that extracts 21 of its 22 files.

The dashboard always says how the database was built. A buildless or partial extraction is listed above the alert counts, so a count of 0 is never read as "no problems": only a traced scan that extracted every file is conclusive.

Each alert shows its rule, severity and the data-flow path. Fixes go through change sets.

MC/DC Coverage#

Statement, decision and modified condition/decision coverage, measured by running instrumented code. Open it from the tile or Noyce Compliance: Open MC/DC Coverage.

Coverage is measured per module, with a test driver for each:

  1. Write a driver under tests/mcdc/ that exercises one source file, and name the file it covers in a comment: // @coverage-source ../AUTO_SEQUENCE.c.
  2. Pick the module and select Measure module. Noyce IDE builds it with LLVM's MC/DC instrumentation, runs the driver and reads the result. Each run is a background job you can cancel, with a five-minute limit.
  3. Generate Coverage Tests has an agent write and check tests for the decisions shown, and Fix Uncovered Decisions gives the decisions still missing independence pairs to the coding agent. Both open Agent output so you can follow the work.

Until a module is measured, its obligations are counted and its coverage reads 0% with the note "a structural zero, not a result".

Note

MC/DC needs LLVM/Clang 18 or newer. With only GCC and gcov installed you get statement and branch coverage, and MC/DC reads "unavailable".

Data & Control Coupling#

Which components call and share data with which, and whether a requirement-based test exercises each coupling. Open it from the DC/CC Analysis tile.

On the Canister copy coupling coverage is shown as not measured: no executed requirement-based test exists yet, so no coupling can be counted as exercised. That is the honest state, not a failure of the tool.

Object Code Traceability#

For DO-178C A-7(9) at Level A: object code that no source line accounts for, such as soft-float helpers, C runtime start-up and the reset vector, each of which needs a named person's justification. Open it with Noyce Compliance: Open Object Code Traceability.

Limitation

This view reads an analysis produced outside it: the view suggests npm run socta -- --project <path>, a script in the Noyce IDE source repository that is not available in the installed app. It needs a linked image and arm-none-eabi-objdump.

Test Explorer#

Finds the project's tests, runs them with Run All, drafts new ones with AI Generate, and records test runs on the target as verification evidence. Open it with ⌘⌥N then T.

Cyber Assurance#

A software bill of materials from the project's real manifests, matched against known vulnerabilities and weaknesses. Open it from the tile.

Choose the standard (for example DO-326A / ED-202A) and select Analyze. CVE matching uses OSV and needs a network connection, and it matches by version: a component with no recorded version is not assessed rather than reported clean. Generate SBOM and Export Security Pack write the results.

Quality Trend#

Code-quality metrics computed in the IDE, with snapshots over time. Open it with ⌘⌥N then Q.

Capture Snapshot records today's numbers so later scans show the trend. The function list ranks functions by cyclomatic complexity; Fix with agent on a function hands it to an agent to reduce its complexity.

Analysis Tools#

The catalogue of analyzers Noyce IDE can run, with what is installed and what is recommended for the project. Open it with Noyce Compliance: Open Analysis Tools.
