Unit test generation

Generate a test driver, stubs and a register-file fake for any function in the program model, fill a table of test vectors with expected values from requirements, propose inputs with CBMC, run on the host and track regressions.

Unit Tests builds a test driver for one function at a time from the program model, and keeps its test vectors in a table you edit. Open it with Noyce Test: Open Unit Tests.

Use it#

  1. If there is no model yet, select Build program model. Functions in vendor trees and functions defined in headers are not listed.
  2. Select a function. The view shows its signature, file, the globals it reads and writes, the callees it stubs, and whether register accesses use a register-file fake (from the SVD file, or an architectural address map).
  3. Review the Test vectors. Rows are proposed from the parameter types: boundary, equivalence and robustness values for fixed-width integers, bool, char and size_t. Other types get no proposed values.
  4. Fill each row's expected values. Enter your name in Engineer name first; the row records who filled it and when. Select Save row.
  5. Select Generate driver to write the driver, or Run on host to generate it, build it and run it.

Expected values never come from running the code. Every proposed row starts with its expected values pending: "Pending rows can never pass. Expected values come from requirements or an engineer, never from running the code." A pending row is skipped in the host driver, left out of the target driver, and reads pending in the results.

Inputs and expected values are JSON, for example {"param:x": 1} and {"return": 2}. Inputs can set param:, global:, stub:<callee>.returns (a sequence of returns) and reg:0x… keys; expected values can check return, outputs through pointers, globals, stub call counts and arguments, call order, and registers. Requirement ids link a row to the requirements it verifies.

Propose inputs with CBMC#

Choose MC/DC or Branch and select Propose inputs (CBMC). CBMC searches for inputs that reach each coverage goal of the function, with the generated stubs, and adds the new inputs as rows (origin cbmc-mcdc or cbmc-branch) with expected values pending. Goals CBMC could not reach are listed; that is not a proof that they are unreachable. Inputs CBMC cannot set (structures, function pointers, nested pointers) are listed under Inputs not proposed. CBMC must be installed; see Formal Verification.

Run and compare#

Run on host builds the driver with the generated Makefile (clang unless CC is set) using Unity, runs it, and records the run. Latest run shows pass, fail, pending and not run. Each run carries the note that host execution does not establish target compatibility, timing or peripheral behaviour (DO-178C 6.4.1).

Regression compares the latest run with the previous run, or with the latest run tagged with the current document-set baseline, and lists rows that regressed, were fixed, are new or were removed. Flaky rows passed and failed with the same source and inputs.

Limitation

Runs are tagged with the document-set baseline by reading .noyce/set-baseline.json, but the baseline is stored at .noyce/documents/set-baseline.json. In this release runs are therefore never tagged, and comparing with Current set baseline finds no earlier run. Compare with Previous run.

Run on the target#

Select Copy driver to tests/target to put the generated target_<unit>.c in tests/target/. Test Explorer's Run on target, and On target below the vectors (the target verification flow), then build it into the firmware test image:

  • The driver is compiled in place of the unit's source, so the unit is linked once. It is self-contained: its stubs are inlined.
  • Every symbol the driver defines on the unit's behalf (the stubs, their controls, test-owned globals) gets a name private to that file (noyce_t_<unit>__<name>), so the firmware's real collaborators and globals still link beside it.
  • One driver per source file per image: two functions of the same file cannot be in tests/target/ together (the image would link that file twice). Keep one, run, then swap.
  • A driver for a function in the file that defines main() cannot run on the target; the test image replaces that file.

Limitation

Target unit runs are built, linked and checked against a fake device; they have not been run on hardware.

Files#

Path under .noyce/ Holds
tests/<file>__<function>.vectors.json The vector table (schema noyce.unit-vectors/1).
tests/build/<unit>/ The generated host driver test_<unit>.c, target driver target_<unit>.c, stubs, register-file fake, Makefile and CBMC harness.
tests/unity/ The bundled Unity framework.
tests/runs/<unit>/ One record per run, tagged Measured.

Limitations#

  • Target runs of generated drivers are unverified on hardware. Only one function's driver per source file can be in an image.
  • The register-file fake stores values only; peripheral side effects and timing are not simulated.
  • CBMC runs with the host architecture and a fixed unwind of 16, so its proposals are bounded.
  • Structures passed by value, nested pointers and function pointers get no proposed inputs.
  • Comparison with the document-set baseline does not work (see above).
  • Firmware that needs Arm-only instructions or linker symbols does not build on the host.
