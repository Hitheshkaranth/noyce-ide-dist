MISRA rule engine

Noyce IDE's own MISRA C:2012 checker, which reads the program model rather than matching text. How many guidelines it implements, the project rule set in .noyce/rules.json, deviations, the Guideline Compliance Summary and the comparison with cppcheck.

Noyce IDE checks MISRA C:2012 (including Amendments 1 to 4) with its own rule engine, which reads a clang-parsed model of the code rather than matching lines of text. It runs next to cppcheck, not instead of it: where the two disagree you see both, and nothing is merged. Open MISRA Diagnostics and select Scan; see Analysis & proof for the rest of the view.

How many guidelines are checked#

The engine implements part of MISRA C:2012. It does not claim full compliance checking, and the count is not fixed in these docs: it is read from the guideline catalogue that ships with Noyce IDE (services/noyce-core/rules/misra-c-2012.json, one entry per guideline with implemented: true or false).

The MISRA Diagnostics page subtitle shows the count for your last scan, for example "Guidelines checked: n of total (MISRA C:2012 rules and directives)", and "· n TUs not checked" when some translation units could not be checked. Before any scan it reads "Guidelines checked: Not measured (MISRA C:2012)". Both numbers count rules and directives.

No guideline text is shipped; it is MISRA's copyright. If you hold a licence, put headline texts in .noyce/rules/headlines.json as {"Rule 10.4": "…"} and the Compliance Summary shows a Headline column. There is no import screen for this file.

Some rules cannot always be decided from the code alone. For those the engine reports a possible violation with its reasoning instead of a violation.

Run a scan#

Scan in MISRA Diagnostics runs cppcheck and the rule engine together. The rule engine shows "Rule engine: x/y TUs · file" while it runs, with Cancel rule scan. It times out after 120 seconds by default; the cppcheck budget setting in the view also sets the rule engine's time limit. A scan that times out or is cancelled reads "Not measured — timed out" or "Not measured — cancelled", never compliant.

From a terminal, noyce analyze runs the same scan. Results are written to .noyce/analysis/rules/results.json.

Code classified as vendor code (for example Drivers/, CMSIS/, HAL, Middlewares/, third_party/) is excluded automatically and reported separately under Excluded adopted code.

The project rule set#

.noyce/rules.json sets which guidelines apply to your project. There is no editor for it in the IDE; write it by hand. Without the file, every implemented guideline is enabled:

json
{
  "schema": "noyce.rules-config/1",
  "edition": "MISRA C:2012",
  "enabled": ["*"],
  "disabled": ["Rule 15.5"],
  "recategorize": { "Rule 15.7": "required", "Rule 2.7": "disapplied" },
  "exclude": ["src/generated/**"],
  "timeoutSeconds": 300
}
Field Meaning
schema, edition schema must be noyce.rules-config/1 and edition must start with MISRA C:2012 (the catalogue's longer edition name is accepted). Anything else discards the whole file and applies the defaults, with a "Rule configuration problems" notice.
enabled, disabled Guideline ids such as "Rule 10.4", or "*".
recategorize Per MISRA Compliance:2020: raise a guideline's category (advisory → required → mandatory), or set an advisory guideline to disapplied. Lowering a category is ignored with a notice.
exclude Path globs relative to the project root. * does not cross /; ** does.
timeoutSeconds The rule engine's time limit (1 to 1800).

Unknown guideline ids and malformed fields are reported in the Compliance Summary under Rule configuration problems.

Guideline Compliance Summary#

The Compliance Summary tab gives one row per guideline, in the style of MISRA Compliance:2020: Guideline, Kind, Category (with "re-categorised from …" where you changed it), Compliance, Violations, Possible and Deviations. Tiles and filters count Compliant, Compliant with deviations, Violations, Disapplied and Not checked.

A guideline is:

  1. Disapplied if your rule set disapplies it;
  2. Not checked if it is not implemented, not enabled, or was not run;
  3. Violations if any violation or possible violation remains;
  4. Not checked if the scan was incomplete: a translation unit failed to parse or timed out. One file that fails to parse turns every guideline without findings into Not checked rather than Compliant;
  5. Compliant with deviations if every finding is covered by an approved deviation;
  6. Compliant otherwise.

Deviations#

A finding counts as compliant with deviation only when a deviation in Evidence Records → MISRA deviations covers it: same rule (or *), matching file and lines or vendor directory, status approved, with a rationale, an assessed risk, an approval date and an approver who is a person on the roster. A mandatory guideline cannot be deviated.

Warning

The rule engine reads deviations from .noyce/process/deviations/ and the roster from .noyce/process/roster/ (one file per record, as the IDE saves them), plus anything still in the older single files. When a project keeps no roster at all, any approver who is not an AI agent is accepted.

Disagreements with cppcheck#

The Disagreements tab compares the rule engine's findings with cppcheck's MISRA addon, for the rules both implement: Only Noyce rule engine, Only cppcheck, Agreed locations and Outside rule overlap, then a table of each disagreement. "Disagreements are reviewed, not merged." It needs a completed run of both.

MISRA C++:2023#

C++ translation units are checked against MISRA C++:2023, and C translation units against MISRA C:2012: each rule set runs only on its own language, and one project can have both. A unit is C++ when its compile command selects C++ (-x c++, or a g++ / clang++ / c++ driver) or its file ends in .cpp, .cc, .cxx or .C. The C++ standard appears only when the last scan found at least one C++ unit.

The engine implements a first slice of 31 of the 179 MISRA C++:2023 guidelines. All 31 are decidable rules whose construct is unambiguous in the clang AST: C-style, functional and reinterpret_cast casts, pointer/integer casts, null pointer constants other than nullptr, goto, unbraced bodies, else if chains, the comma operator, unary +, several variables in one declaration, asm, bit-fields, union, virtual inheritance, virtual / override / final, non-explicit converting constructors and conversion operators, overloaded && / || / unary &, pointer exception objects, throw; outside a handler, program-terminating functions, #pragma, atof-family functions, offsetof, <cstdarg> and std::vector<bool>. The catalogue is services/noyce-core/rules/misra-cpp-2023.json.

  • The page subtitle adds "· n of 179 (MISRA C++:2023, m C++ TUs)" after the MISRA C count.
  • C++ findings appear in the Findings tab with the rule shown as "MISRA C++:2023 Rule 9.6.1".
  • The Compliance Summary tab gets a MISRA C:2012 / MISRA C++:2023 switch. The C++ summary uses the same compliance rules as MISRA C, over C++ units only.

Warning

The guideline ids, categories, decidability and scope in the C++ catalogue come from one public listing (codeql-coding-standards rules.csv) and were not cross-checked against a second source. Every entry is marked review: "unconfirmed", and the C++ summary shows a "Guideline categories unconfirmed" notice. Confirm the categories against your licensed copy, and correct one with cpp.recategorize until then.

To configure C++, add a cpp section to .noyce/rules.json beside the MISRA C settings:

json
{
  "schema": "noyce.rules-config/1",
  "edition": "MISRA C:2012",
  "disabled": ["Rule 15.5"],
  "exclude": ["src/generated/**"],
  "cpp": {
    "disabled": ["Rule 9.6.1"],
    "recategorize": { "Rule 8.2.2": "mandatory" }
  }
}

A C++-only project can put "edition": "MISRA C++:2023" at the top level instead; MISRA C then uses its defaults for any C units. The cpp section takes the same enabled, disabled, recategorize and exclude fields. Without its own exclude it inherits the top-level one. Ids from the other standard are reported as unknown. Headlines for C++ guidelines go in the same .noyce/rules/headlines.json, keyed by id ("Rule 8.2.2"). Deviations work as for MISRA C.

C++-specific limitations:

  • Templates are checked as written (the declared pattern), not per instantiation. A construct that only arises for a particular template argument is not reported.
  • virtual / override / final (Rule 13.3.1) resolves base classes among the classes the translation unit sees. A base defined only outside the project gives no finding.
  • Exceptions in the licensed text are not applied unless they are certain. Rule 8.2.2 exempts only casts to void, Rule 8.2.5 exempts nothing, and Rule 13.3.1 also reports overriding destructors without override. These rules may over-report until reviewed against the licensed copy.
  • The program model builds no control-flow graph for C++ functions containing try/catch, throw or range-based for (no implemented C++ rule needs one).
  • The C++ qualification corpus (qualification/corpus/misra-cpp-rules, engine id misra-cpp-rules) is Noyce's own, not the licensed MISRA C++ Example Suite. See qualification/known-problems/misra-cpp-rules.md.

Limitations#

  • Only part of MISRA C:2012 is implemented; directives are not checked. The count is in the page subtitle.
  • Only 31 of 179 MISRA C++:2023 guidelines are implemented, with categories from one unconfirmed public listing (see MISRA C++:2023).
  • The rule engine's results are not yet counted as A-5 evidence; coding-standard objectives read cppcheck.
  • In the Findings tab a possible violation looks like a violation; only the Summary's Possible column separates them.
  • No guideline text; headlines only from your own .noyce/rules/headlines.json.
  • The qualification corpus is Noyce's own, not the licensed MISRA Example Suite. Known problems include Rule 11.7 not being detectable end to end (clang rejects the construct), and essential-type rules that need review against the licensed edition. See qualification/known-problems/misra-rules.md and Qualification kits.
  • The MISRA tile in Quality Trend uses a separate scan, not the rule engine.
