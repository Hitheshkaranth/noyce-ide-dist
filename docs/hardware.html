Hardware

Register Knowledge from your reference manual, firmware memory and stack, pin configuration, schematics and BoM, fault decoding, serial and Modbus, and live debug with a probe.

Open any hardware surface from the Hardware activity bar icon, its tile on the start tab, or a Noyce Hardware: command.

Register Knowledge#

Your microcontroller's reference manual, turned into a searchable register database where every fact cites the page it came from. Open it from the tile or Noyce Hardware: Open Register Knowledge.

How it gets the manual. When you import a TI or ST project with the Import Project wizard, Noyce IDE identifies the part, downloads its reference manual and indexes it. You can also index a manual you already have with Choose PDF…, and rebuild the index with Re-index.

How to use it

  1. Type a register or field name in the search box, for example GPIOAFSEL.
  2. Select the register to see what the manual says about it, its offset and reset value, the page it is documented on, every base address it appears at, and its bit fields.
  3. Switch to Rules to see the documented constraints for that register, such as unlock sequences and commit-control requirements.
  4. Link code finds where your firmware writes each register, directly or through the vendor HAL, and Build graph connects registers, rules and code.

The manual and the index are stored in .noyce/manuals/ and .noyce/knowledge/.

Firmware Memory & Stack#

Flash and RAM use by module, symbol and section, worst-case stack depth, and what changed since the last build. Open it with Noyce Hardware: Open Firmware Memory & Stack.

What it needs: a GNU linker map (-Wl,-Map=<name>.map) or TI Arm linker map from a build of the project. GNU builds need -fstack-usage .su files for worst-case stack depth.

Tabs show Modules, Symbols, Sections, Stack roots and Since last build, with a budget card for each memory region. The first build becomes the baseline that later builds are compared against.

Note

Firmware Memory reads TI Arm linker maps too: memory regions, sections, per-function sizes and per-object totals. Build the project in CCS or in Build Pipeline so a .map exists. TI does not produce -fstack-usage records, so for a TI map the view shows the configured stack size and says the worst-case depth is not established.

Pin Configurator#

The chip's package with every pin's function, taken from your project. Open it with Noyce Hardware: Open Pin Configurator, or open an STM32 .ioc file.

  • STM32: the configuration is read from the .ioc, and edits are written back to it.
  • TI Tiva: there is no .ioc, so Noyce IDE reconstructs the pin map from the TivaWare calls in your C source (GPIOPinConfigure, GPIOPinType…, SysCtlPeripheralEnable).
  • The pin configuration is detected when the project opens; Detect Pin Config from Loaded Project re-scans on demand.
  • Generate init code writes initialisation code for the current configuration.

Peripheral Registers#

The peripherals and pins your project uses, grouped by peripheral, with each pin's signal and the net label from your code. Open it with Noyce Hardware: Open Peripheral Registers.

This view is derived from the pin configuration. It does not read registers from the target; for live values, use the Debug Probe and Memory View.

Register Inspector (SVD)#

A CMSIS-SVD browser and decoder: look up any register's fields, or paste a value and see each field decoded. Open it with Noyce Hardware: Open Register Inspector.

Where the SVD comes from. When the project contains an SVD file, the view opens on it and says "Loaded from the workspace." It uses the file named in the noyce.agents.svd.path setting (absolute, or relative to the project folder), or else the first *.svd in the project outside node_modules, .git, out, dist and build. Files over 30 MB are not loaded. To use another file for this session, select Load .svd… and pick it (.svd or .xml).

Then search for a peripheral or register, and paste a value into Decode Register Value to see every field.

Note

With no SVD in the project, the view opens on a small built-in sample device and says so, naming your part when it has detected it. Load your own SVD before trusting the field layout. The same SVD also powers register hovers and completions in the editor; see AI & agents.

Schematic Viewer#

Search a schematic PDF, extract a bill of materials from it, and see an inferred component graph. Open it from the Schematic + BoM tile.

How to use it

  1. Pick a PDF from PDFs found in this project, or Open PDF…. The pages render; nothing is analysed yet.
  2. Select Analyze (or Find, which analyses first). Noyce IDE extracts every piece of text with its position: through LiteParse, with PaddleOCR on pages that have almost no text, when the desktop host provides them; otherwise with pdf.js and tesseract.js OCR in the window. The header then reads how many text items and parts it found.
  3. BoM opens the bill of materials built from the reference designators it found: quantity, class, value and designators. Select a designator to jump to it on the page.
  4. Graph opens the inferred component graph.
  5. Find (⌘F) searches every extracted word, net labels included.
  6. Open in BoM Studio hands the BoM over for distributor lookups and Excel export.

Important

The component graph is inferred from the layout, not parsed from a netlist: a NET edge joins parts near the same net label, and a dashed PROXIMITY edge joins parts placed close together. Treat it as a guide when reading the schematic, not as connectivity evidence.

BoM Studio#

Load a bill of materials from Excel or CSV, or take the one extracted from a schematic, and enrich each part with distributor data. Open it with Noyce Hardware: Open BoM Studio.

Distributor enrichment uses Mouser and DigiKey. Enter their credentials with these commands from the Command Palette. Each opens a password prompt, and what you type is stored in the system keychain (VS Code SecretStorage), not in your settings:

Command What it asks for
Noyce Parts: Set Mouser API Key… Your Mouser Search API key
Noyce Parts: Set DigiKey Credentials… Your DigiKey API application's OAuth client ID, then its client secret. Both are kept in the keychain.
Noyce Parts: Clear Distributor Credentials Nothing: it removes the Mouser and DigiKey credentials from the keychain after you confirm

When no distributor is configured and a BoM is loaded, BoM Studio also shows Set Mouser API key… and Set DigiKey credentials… buttons that open the same prompts.

The setting noyce.parts.preferredDistributor is mouser (default) or digikey: which one is asked first. The other is asked when the first has no answer. If only one is configured, it is used whatever this says.

Each enriched row shows which distributor answered. The credentials never leave the extension host: they are not logged and are never passed to the BoM Studio page itself.

Note

Earlier versions kept these credentials in the plain settings noyce.parts.mouser.apiKey, noyce.parts.digikey.clientId and noyce.parts.digikey.clientSecret. On the first start after updating, Noyce IDE moves any of them it finds (in User, Workspace or folder settings) into the keychain, removes them from every settings file they were in, and tells you once. A credential already in the keychain is kept. A value committed to a repository's .vscode/settings.json before the move is still in that repository's history, so rotate it.

Export .xlsx and Export .csv write bom.xlsx or bom.csv to .noyce/bom/ in the project.

Fault Analyzer#

Decode an ARM Cortex-M HardFault from its fault registers. Open it from the HardFault Analyzer tile.

  1. Paste the register dump from your debugger: CFSR, HFSR, BFAR, MMFAR and the stacked R0–PC and xPSR.
  2. Optionally load the build's .map so addresses resolve to function names.
  3. Select Decode Fault. The analyzer names the fault, explains each status bit, shows the exception frame, and recommends where to look.

It decodes what you paste; it does not read faults from a running target.

Serial Monitor#

A UART or USB serial console with real port access. Open it with ⌘⌥N then R.

Send text or hex. Debug with AI saves the session to .noyce/serial/latest.log and hands it to an agent with the question you ask.

Debug Probe and Memory View#

Attach a debug probe through probe-rs, which is built into Noyce IDE. Open them with Noyce Hardware: Open Debug Probe and Open Memory View.

  • Debug Probe lists connected probes, finds your chip in the probe-rs registry, attaches, and gives you halt, run, step, reset and reset-and-halt. It can also flash an image and verify it.
  • Memory View reads live target memory once a probe is attached.

STM32 Debug State#

The STM32 Debug State view in the Noyce IDE sidebar shows, for the attached target:

  • Probe Status: each probe on the USB bus, and whether a target is attached. When none is, select Attach Debug Probe.
  • Core Registers: the core registers, with values that changed since the last read marked.
  • Memory Watches: addresses you want to keep an eye on. Select + (Add Memory Watch), then enter either a hex address such as 0x20000000 or a symbol name such as adc_samples, then a label and a size in bytes. A symbol name is looked up in the project's GNU ld .map file, the newest one in the workspace, so build the project first. The size defaults to the symbol's size when the map gives it, and to 4 bytes when it does not; change it if the variable is larger. If the name is not in the map, the view says so and asks again. Each watch shows the bytes at that address in hex, with the symbol name in its label. Bytes that changed since the last read are marked. Watches are kept with the workspace; remove one with its × button.

The view reads through probe-rs. While it is visible and a target is attached, it re-reads the core registers and memory watches every second. Set noyce.stm32.debug.refreshIntervalMs to change the interval (250 ms minimum), or to 0 to turn auto-refresh off. It also updates when you select Refresh, add or remove a watch, or attach or detach. A symbol is resolved to its address when you add the watch: after a rebuild that moves it, add the watch again. Watches read memory, not expressions.

Modbus Monitor#

A Modbus master over a serial port: choose the port, baud rate and slave ID, and read holding registers. Open it with Noyce Hardware: Open Modbus Monitor.

Note

The register table starts as an example register map and is labelled so. Replace the addresses and names with your device's register map. The serial connection is real.

Simulated surfaces#

Signal Viewer, Live Data Dashboard, HIL Test Runner, Energy Profiler and Data Recorder show generated data for demonstration, and each says so with a banner. Do not use their numbers as measurements. Data Recorder's export writes the generated samples to .noyce/recordings/. See Known limitations.

FPGA Workspace#

FPGA Workspace (⌘⌥N then F) and Synthesis Dashboard lay out what an FPGA flow will show: HDL sources, constraints, and a synthesis report with utilization, timing and power.

Warning

FPGA synthesis is not connected in this release. Run synthesis says that Vivado was not run, and the figures in both views are an example, marked as one, not results for your project.
