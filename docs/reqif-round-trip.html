ReqIF round trip, suspect links and change impact

Import a ReqIF 1.2 file from your requirements tool, send Noyce IDE's trace links back to it, see which links went suspect when a requirement changed, and walk what a change affects.

Your system requirements usually live in a requirements tool such as IBM DOORS Next, Siemens Polarion or Jama Connect. Noyce IDE exchanges them with that tool through a ReqIF 1.2 file. It does not sync with the tool directly; see ALM connectors for the state of live connectors.

All of this happens in Requirements & Evidence. Open it from the Requirements tile or Noyce Compliance: Show Requirements Explorer. The view has four tabs: Software requirements, System requirements (imported) (shown once something is imported), Suspect links and Change impact.

Import a ReqIF file#

  1. Select Import CSV / ReqIF… and choose the .reqif file exported from your requirements tool.
  2. The notice says how many system requirements were imported, which tool wrote the file, how many objects, relations and specifications it held, and whether any trace link has gone suspect.

What is read:

  • The whole ReqIF 1.2 structure: the header, all seven datatypes (string, XHTML, integer, real, Boolean, date, enumeration), spec types with their attribute definitions and defaults, SPEC-OBJECTs, the specification hierarchy, SPEC-RELATIONs and relation groups. Vendor tool extensions are kept but not interpreted.
  • For each SPEC-OBJECT, the requirement's id comes from ReqIF.ForeignID (else the object's identifier), its title from ReqIF.Name or ReqIF.ChapterName, and its text from ReqIF.Text. The other attributes are kept for display and for the suspect-link check. XHTML text is also converted to plain text.
  • An object with no identifier or no text is skipped, and the notice says why.

What is kept: a copy of the file under .noyce/requirements/reqif/, named by the start of its SHA-256, and an entry in .noyce/requirements/reqif/index.json. Export writes into the latest kept copy.

Limitation

  • The SPEC-RELATIONs and hierarchy in the imported file are counted but not turned into Noyce trace links. Noyce IDE's trace links come from your HLRs and LLRs naming their parents.
  • .reqifz archives are not read. Extract the .reqif file and import that.
  • The file is not validated against the ReqIF schema.
  • Only Import CSV / ReqIF… in Requirements & Evidence does the round trip. Import file… in Requirements Authoring imports the same requirements, but it does not keep the file for export and does not check the trace links before and after. Use Requirements & Evidence for ReqIF.

CSV, Markdown tables and Excel workbooks (.xlsx, .xls) import through the same button as plain system requirements, without round trip.

Export the trace back#

Select Export ReqIF with trace. Noyce IDE first re-checks the trace links, then writes .noyce/requirements/reqif/exports/<name>-noyce-trace-<time>.reqif, and records the export in the audit trail.

  • If a ReqIF file was imported, the export is that file with Noyce content added, and nothing else changed. The additions all have identifiers starting _noyce-x-: a relation type "Noyce trace link", one SPEC-RELATION per trace link (source is the refining requirement, target is its parent), and a specification "Noyce software requirements" holding your HLRs and accepted LLRs. Exporting again replaces the previous Noyce content, so the file does not grow.
  • If no ReqIF file was imported, the export is a new ReqIF 1.2 file holding the system requirements, the HLRs, the accepted LLRs and the links.

Each exported link carries noyce.linkKind and noyce.linkStatus (current, suspect or cleared), so a suspect link reaches your requirements tool marked as suspect. Only requirement-to-requirement links are exported (HLR to system requirement, LLR to HLR); links to code, tests and coverage are not. A link whose end is missing is skipped, and the notice lists it.

Import the exported file into your requirements tool to see Noyce IDE's trace there.

Suspect links#

A trace link records what both of its ends said when it was last reviewed. When one end changes, the link turns suspect until a person reviews the change.

Which links. An HLR that names an imported system requirement as its parent (HLR → system), and an accepted LLR that names an HLR (LLR → HLR).

What is compared. A SHA-256 of each end's id, title, text and significant attributes. For an HLR these are its verification method, DAL, derived flag and safety flag; for an LLR, its verification method and derived flag; for a system requirement, its imported attributes. Bookkeeping attributes such as modified-by, modified-on, created-by and owner are not hashed, so a re-export from the requirements tool that only touched those does not raise a suspect link.

When it is checked. When Requirements & Evidence opens, when you select Re-check links, before and after a ReqIF import, and before an export. Editing an HLR does not flag its links until one of these happens.

Clearing a suspect link.

  1. Select the link. Review the change shows which end changed, a word diff of the text as reviewed and now, any changed attributes, and the old and new content hash.
  2. Choose who reviewed it under Reviewed by. Only people on the roster are offered.
  3. Under Why the trace still holds, say why the link is still right (at least 15 characters).
  4. Select Review & clear.

The review is written to the audit trail in the reviewer's name first; that ledger entry is the signature. Only then does the new text become the link's baseline. If the ledger write fails, the link stays suspect. Cleared links are listed under Cleared by review with the reviewer, rationale and signature.

If both ends change back to what was reviewed, the link stops being suspect by itself.

Note

Clearing a suspect link needs a person on the roster, but it does not check that the reviewer is independent of whoever changed the requirement. Choose the reviewer accordingly.

Links are stored one file per link under .noyce/requirements/trace-links/, so two branches adding links merge cleanly. See Command line, CI and team use.

Change impact#

From a changed requirement, list everything it affects. Open the Change impact tab, select Impact on a row of the system requirements, or select Show change impact on a requirement or a suspect link.

The walk goes from the changed requirement down to the requirements that refine it (system requirement, HLR, LLR), then to:

Tile What it lists
Requirements The changed requirement and every requirement refining it, with the one it was reached from.
Code Implementation points: @req tags and the HLR's implemented-by links.
Tests Tests tagged with or linked to an affected requirement.
Results Those tests' results in the latest sealed test run. "No sealed test run" when there is none.
Coverage records Measured coverage records over the affected source files. "No measured coverage" when there are none.

An id that is not in the project is listed under Not in the project. Sample data has no workspace trace, so change impact is not offered for it.

Limitations#

  • No live connection to DOORS Next, Polarion or Jama; exchange is by ReqIF file. See ALM connectors.
  • .reqifz archives are not read.
  • ReqIF relations and hierarchy from the requirements tool are not imported as trace links.
  • Only requirement-to-requirement links are exported.
  • Suspect links are re-checked on open, on Re-check links and on import or export, not as you edit.
  • Clearing a suspect link does not check reviewer independence.
