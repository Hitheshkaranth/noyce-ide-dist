Tool qualification kits

The DO-330 qualification data Noyce IDE produces for its own verification engines - operational requirements, oracle corpora, signed results, known problems and the kit that bundles them - and how to build, verify and re-run a kit.

When you take certification credit for a tool's output without verifying that output by other means, DO-178C §12.2 asks you to qualify the tool. Noyce IDE's verification engines, such as host coverage or the MISRA rule checker, are such tools. For each one, Noyce provides qualification data and assembles it into a signed kit for one exact engine version.

Important

A kit is qualification data, not a qualification. Its Tool Qualification Plan and Tool Accomplishment Summary are templates that only you, the applicant, can complete: certification basis, operational environment, credit sought and liaison. The criterion and TQL shown for each engine are Noyce's proposal; you confirm or replace them in your PSAC.

The engines#

Engine id Engine Known problems file
cov-host Host structural coverage (statement, decision, MC/DC) yes
cov-probe Target structural coverage probes yes
coupling Measured data and control coupling yes
object-coverage Object-code coverage and source-to-object traceability yes
timing-stack Worst-case stack usage and timing measurement none recorded
metrics Code metrics and flowgraphs none recorded
concurrency Concurrency and shared-data analysis yes
unit-gen Unit test generation and execution yes
misra-rules MISRA C rule checker yes

Each is classified as §12.2 criterion 3 (a verification tool whose defect could fail to detect an error), which is TQL-5 at levels A to D. The rationale, and when another criterion would apply, is shown for each engine.

Where the data lives#

These files are in the Noyce IDE source repository, not in your project:

Artefact Location
Tool Operational Requirements (TOR), with @tor ids docs/qualification/<engine>/tor.md
Oracle corpus: inputs with independently reasoned expected results qualification/corpus/<engine>/<case>/ (case.json, expected.json, README.md, sources)
Known problems: investigated defects, their TOR, root cause and credit impact qualification/known-problems/<engine>.md
Differential comparisons against a reference tool qualification/differential/
Results record of a corpus run .noyce/qualification/<engine>/<engine version>/results.json
Built kits .noyce/qualification/kits/<engine>/<engine version>/
In-situ re-run kits .noyce/qualification/in-situ/<engine>/<engine version>/

The engine version is <git commit>[-dirty]+<digest of the engine's source files>, so a kit identifies exactly which code it qualifies.

Run the corpus#

From a Noyce IDE source checkout:

Terminal
noyce qualify --engine cov-host     # one engine
noyce qualify --all                 # every engine with an adapter

npm run qualification:run -- --engine <id> does the same. Each case runs in a fresh temporary copy. A TOR passes only when at least one case verifies it and all its cases pass; an untested TOR fails the run. The results record carries a SHA-256 digest of its content and, if you have a signing key, an Ed25519 signature (results.sig.json).

The corpus runs use the same tools as the engines: for coverage, a clang with -fcoverage-mcdc, llvm-profdata, llvm-cov and nm; for the sidecar engines, the noyce-core binary. The runner needs Node 26.

Build a kit#

You sign kits with your own Ed25519 key. Noyce IDE never generates one for you. Create it once:

Terminal
noyce kit --init-key                # or: npm run qualification:kit -- --init-key

The private key goes to ~/.config/noyce/qualification-signing.key (mode 600; NOYCE_SIGNING_KEY chooses another path), and the public key to qualification/signing-keys/ in the checkout, where verification looks for trusted keys.

Then build, verify and export:

Command Does
noyce kit --engine <id> or --all Builds and signs a kit from the latest results.
noyce kit --engine <id> --allow-dirty Builds a kit from a run taken on uncommitted code, marked DRAFT on every page and in the manifest.
noyce kit --verify <kit-dir> Checks every file against the signed manifest and the signature against the trusted keys.
noyce kit --verify-results <results.json> Checks one results record and its signature.
noyce kit --in-situ --engine <id> [--dest <dir>] Exports the in-situ re-run kit.
noyce kit --status [--engine <id>] Readiness and kit state for each engine.

--public-key <pem> adds a trusted key for either verify command.

A kit is refused, never built with a caveat, when the latest run has a failing or erroring case, an untested TOR, was a partial run of selected cases, has an altered record or signature, or was produced by a different engine version, corpus or TOR set than the checkout building the kit. A run on uncommitted code is refused unless you pass --allow-dirty.

A kit contains:

  • 01-TOR, 02-TOVV (verification cases, procedures and results), 03-KNOWN-PROBLEMS, 04-TCI (Tool Configuration Index), 05-TQP-TEMPLATE and 06-TAS-TEMPLATE, each as Markdown and as a formal .docx;
  • results/results.json with its signature, tci.json, the engine's corpus, kit.html, INDEX.md, the signer's public key, and manifest.json with manifest.sig.json covering every file.

The in-situ re-run kit#

The in-situ kit lets the applicant re-run the corpus in their own environment and sign their own results. Hand them the folder:

  1. Check out Noyce IDE at the commit the kit names and install its dependencies.
  2. Install the production toolchain. The tool overrides are the same as in development (NOYCE_COV_CC, NOYCE_COV_PROFDATA, NOYCE_COV, NOYCE_COV_NM, NOYCE_CORE_BIN, NOYCE_CBMC).
  3. Create their own key: node tools/insitu.mjs init-key.
  4. Run NOYCE_ROOT=/path/to/noyce ./run.sh.

They get their own signed results record and a signed comparison.json / comparison.md: case-by-case and TOR-by-TOR agreement with the shipped results, and every toolchain or platform difference. Exit 0 means their run passed and agrees; 1 it failed or differs; 2 an environment problem. Agreement is evidence for their Tool Qualification Plan, not a qualification by itself.

In the IDE#

Open Evidence Records → Tool qualification. Below the project's tool register, the kits table lists the nine engines with Criterion · TQL at the project's level, Latest run, Version and Kit. Select an engine for Build kit, Verify kit and Export in-situ kit. Every disabled button says why, and a refused kit lists the builder's reasons.

Limitation

The kit actions run from a Noyce IDE source checkout and read that checkout's .noyce/qualification/, not your firmware project's. An installed app without the corpus says "Kit status not measured" and builds nothing. Run noyce qualify and noyce kit from the checkout root (or pass --out <checkout>/.noyce), or the panel will not see the results.

Limitations#

  • Kits are built only from a Noyce IDE source checkout; the installed app does not include the corpus or the kit builder.
  • The corpus runner needs Node 26.
  • timing-stack and metrics have no known-problems file; that means none is recorded, not that the engines are free of defects.
  • The TQP and TAS are templates you complete.
