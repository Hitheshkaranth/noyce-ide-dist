Requirements & traceability

Where requirements come from in Noyce IDE, how to write and import them, how low-level requirements are drafted from code, and how to see every trace link.

Noyce IDE builds one requirements picture from three sources: requirements you write or import, @req and @verification tags in source code, and the requirements sections of your DO-178C documents. The register, the graphs and the Compliance Dashboard all read the same picture.

Because there is one picture, fixing a trace gap in any view fixes it everywhere. If the register and the dashboard ever disagree, rescan: the graph is rebuilt whenever the files in .noyce/requirements/ or .noyce/documents/ change.

Requirements & Evidence#

The register of every requirement with its status and trace state. Open it from the Requirements tile or Noyce Compliance: Show Requirements Explorer.

  • The counters at the top show requirements that are trace-ready, coverage gaps, and requirements with verified evidence.
  • Select a requirement to see its rationale, its linked documents, the system requirement it traces to, and the code that implements it. Open in traceability map jumps to it in the graph.

Note

External ALM tools such as Jama Connect and IBM DOORS Next are not connected; the view says so. Export from those tools to ReqIF or CSV and import the file in Requirements Authoring.

Requirements Authoring#

Write high-level requirements, import system requirements, and check them as you type. Open it with Noyce Compliance: Open Requirements Authoring.

  • High-level requirements are written into the SRS document (SRS-001), so the document and the register never disagree.
  • System requirements import from CSV, ReqIF, or a Markdown table. The imported file's hash is recorded, so you can show which version of the customer's requirements you worked from.
  • The live check flags a requirement with two "shall"s, a TBD, or no parent, and will not let it be marked reviewed or baselined until it is fixed.

Recover system requirements from a prototype#

When the firmware already works but its system requirements were never written down, run Noyce Compliance: Recover System Requirements from Prototype. Requirements Authoring opens with a Recovered from prototype section of candidate system requirements, read from the project's C sources and headers, STM32CubeMX .ioc files, and any interface control spreadsheets or CSVs. No model is involved: the same project always gives the same candidates.

A candidate is only a proposal. Accept, edit or reject each one; an accepted candidate becomes a system requirement. Every decision is recorded in the audit trail with who made it, and the candidates and decisions are kept in .noyce/requirements/system-recovery.json.

Low-Level Requirements#

Noyce IDE drafts low-level requirements from the code and shows every gap between functions, LLRs and HLRs. Open it with Noyce Compliance: Open Low-Level Requirements.

  1. Select Draft from code. Noyce IDE proposes one LLR per function from its signature, body and annotations and, when the reference manual is indexed, the registers it touches. No model is needed.
  2. Optionally select Draft intent with model to have your model state each function's required behaviour, and Suggest parents with model to propose the HLR each LLR refines.
  3. Review the drafts and accept or reject each one.

A draft is only a draft. It counts as a low-level requirement once a person on your roster accepts it through a review record. Accepted LLRs are also what CBMC harnesses are generated from.

Annotation Navigator#

Lists every @req and @verification tag in the source. Run Noyce Compliance: Scan Workspace (⌘⌥N then S) to rescan, or open it with Open Annotation Navigator.

Tag a requirement or a test in a comment:

c
/* @req SYS-REQ-014: Forward auto-sequence with limit-switch gating */
/* @verification SYS-REQ-014: test_auto_seq_forward */

Important

A requirement is labelled Verified only when it has an executed test result as evidence. A @verification tag that names a test does not make it evidence, so tagged requirements without a recorded test run read Needs review.

Traceability Graph#

A live graph of requirements and what they link to: low-level requirements, source, tests, and design documents. Open it from its tile or Noyce Compliance: Open Traceability Graph.

The graph rebuilds by itself whenever the requirements or documents in .noyce/ change.

Project Truth Graph#

One view of everything Noyce IDE knows about the project: requirements, code, verification evidence, generated artifacts and objectives, with the links between them and any reference that points at nothing. Open it with Noyce Project Graph: Open Project Truth Graph.
