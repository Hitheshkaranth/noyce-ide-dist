Take a project through DO-178C

The order of work that takes a firmware project from plans to an evidence package in Noyce IDE, with what each step produces and what a person has to sign.

DO-178CAnnex APeople sign; agents draft

This guide follows the path Noyce IDE lays out in the Compliance Run view: plans and standards, requirements, design, code, verification, then the summaries. Noyce IDE does the measuring and drafting. People do the deciding: every objective is closed by a named reviewer on your roster, never by an AI.

Important

Noyce IDE produces evidence and drafts. It does not certify software. Your certification authority and DER decide what is acceptable.

The stages are ordered because each one is checked against the one before: requirements against the plans, design against the requirements, code against the design, and verification against all of them. You can work on several at once; the Compliance Run view shows each stage's progress and suggests the next action for it.

Before you start#

  1. Open the project and connect a model. Document authoring and agent drafting need a model; the measurements do not.
  2. Open Compliance (⌘⌥N then C) and set the framework to DO-178C and the assurance level to your DAL in the header selects. The level is saved with the project's compliance article and printed on document covers.
  3. Open Evidence Records → Roster and add every person who will review, approve or sign. Reviews, approvals and signatures can only be recorded against people on the roster.

Limitation

Set the DAL on the Compliance Dashboard. The Assurance Level in Settings → Compliance Standards is not saved and has no effect. The Compliance Run, Certification Readiness, Coupling and MC/DC views currently assess against Level A regardless of the level you pick.

1. Import the Annex A table you are licensed to use#

The wording of the DO-178C Annex A objectives belongs to RTCA, so Noyce IDE does not ship it. Until you import your licensed copy, plans and summaries are marked DRAFT, not for submission.

  1. On the Compliance Dashboard, expand Licensed Annex A table.
  2. Select Write blank template. Noyce IDE writes .noyce/compliance/annex-a-licensed.template.json.
  3. Fill in applicability, independence and control category for your level, and save it as annex-a-licensed.json in the same folder.

Objective text for the run view is imported separately in Compliance Run → Objective map → Import objective text.

2. Plans and standards#

Open DO-178C Documents. The library holds all 17 life-cycle documents, grouped as Plans (PSAC, SDP, SVP, SCMP, SQAP), Standards (SRSTD, SDSTD, SCSTD), Core (SRS, SDD, ICD, TRACE), Verification (SVCP, SVR) and Summary (SECI, SCI, SAS).

For each plan:

  1. Select Create from template. Sections that can be filled from the workspace, such as the toolchain, the file list and the target, are filled immediately, without a model. PSAC fills most of its sections this way.
  2. Select Propose decisions. An agent drafts each section that needs engineering judgment and marks it PROPOSED, awaiting engineer review. Nothing proposed counts until a person accepts it.
  3. Open Review decisions. For each draft choose Accept, Edit and accept, or Reject with a comment the next draft must answer. Each acceptance is recorded as a review in the audit trail.
  4. Optionally select Run docs swarm (or Author set… for several documents) to have agents write the remaining prose. Each section is saved as it is written, so a stopped run resumes where it left off.

To use your company's Word template, select Document template… → Import from .docx. Noyce IDE lifts the styles, header, footer, page setup and logo, and applies them to every export.

3. Requirements#

High-level requirements live in the SRS. Bring them in from wherever they are today:

  • Requirements Authoring: write HLRs directly, or import system requirements from CSV, ReqIF or a Markdown table. A live check blocks the reviewed status on statements with two "shall"s, a TBD, or no parent.
  • Source tags: @req and @verification comments in code are picked up by Scan Workspace.
  • Low-Level Requirements: drafts one LLR per function from the code. A draft counts only once a person on the roster accepts it.

See Requirements & traceability for each view.

4. Design and code#

  • System Architecture builds a C4 model from the code and exports it for the SDD.
  • MISRA Diagnostics reports coding-standard findings. Fix them with Fix with Noyce, record a MISRA deviation, or leave them open; each fix becomes a change set you approve. See Review AI changes.
  • Code Scanning (CodeQL) and Formal Verification (CBMC) add security and proof evidence.

5. Verification#

  • Test Explorer finds the project's tests and records target test runs.
  • MC/DC Coverage measures statement, decision and MC/DC coverage with LLVM, per module.
  • Data & Control Coupling and Object Code Traceability cover DO-178C A-7(8) and A-7(9).
  • Record each review in Evidence Records → Reviews. Independence is worked out from who wrote the item and who reviewed it; you do not tick a box. A review by an AI, a self-review, or a review by someone not on the roster is never independent.

6. Take a compliance run#

Open Compliance Run and select Take a run. Noyce IDE runs every evidence producer against the current commit and stores the result as a reproducible record.

The run shows, per Annex A table, which objectives are evidenced, unmapped or still open, what each tool reported, and what changed since the previous run. Map producers to objectives with Objective map → Map…; every mapping needs a stated basis. Select Mark baseline to fix a run as your reference.

Here is a real first run on the Canister copy:

Read a first run like this one as a to-do list, not a verdict. Each of the 16 Blocks export lines names a concrete gap and usually the fix: documents not yet baselined, requirements with no parent, a static analyzer that is not registered as a qualified tool, CodeQL include paths that could not be resolved, CBMC that ran on seeded sample input, and a working tree with uncommitted changes. The DAL path above it tells you which stage to work on next.

A run cannot be exported if a producer failed, sample data was used, there is no commit, or the working tree has uncommitted changes.

7. Issue the documents#

In each document's Completion tab, resolve what is left: proposals awaiting review, engineering decisions, evidence the workspace has not produced yet, and cross-document consistency. Then choose the signatories from the roster and select Sign and issue (baseline). The issued revision is frozen with a SHA-256 content hash.

SVR and SAS cannot be issued until the latest compliance run shows executed verification. When the whole set is ready, select Declare set baseline in the library; it records the git commit.

Select Export .docx on any document for a Word copy with your template, numbered headings, tables and figures.

8. Export the evidence package#

On the Compliance Dashboard, select Certification Package. Noyce IDE runs CBMC and CodeQL, gathers the requirements, traceability, analysis, coverage, reviews, documents and audit trail, and writes Markdown, HTML and JSON to .noyce/certification/.

The button stays disabled until there are requirements and every objective has been assessed or reviewed, and the export is refused while the document set has unwaived contradictions.

Note

The package is sealed, not signed. Each section is hashed with SHA-256, and the package digest is anchored to the head of the hash-chained audit trail, so any later change is detectable. It carries no private-key signature.

How Annex A objectives are graded#

Status Meaning
Satisfied The objective's own evidence exists and a person has reviewed it.
Partial Some of the objective's evidence exists, or a project-wide measure suggests progress. A proxy can make an objective partial, never satisfied.
Open / unassessed No mapped evidence yet. This is "not shown", not "failed".
Failing A check that maps to the objective failed.
