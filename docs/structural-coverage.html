Structural coverage

Statement, decision and MC/DC coverage measured on the host with LLVM, target coverage probes, object-code branch coverage from execution traces, and the signed review of what is left uncovered.

DO-178C Table A-7 asks for statement, decision and MC/DC coverage (objectives 5 to 7, depending on level) and, at Level A, for object code that is not traceable to source to be verified (objective 9). Noyce IDE measures coverage in three ways, and shows each with its environment so you can see what kind of credit it supports:

Way Environment State in this release
Host coverage with LLVM Host, with vendor SDK calls stubbed Works in the IDE and the CLI.
Target coverage probes Target One flow in the IDE (Target verification) and the CLI (noyce verify --target): build instrumented, flash, run, collect. Tested against a fake device and real toolchains; not verified on hardware.
Object-code branch coverage Simulator or target trace Disassembly and trace import work in the IDE; no real trace has been ingested yet.

Host coverage (MC/DC Coverage)#

Open MC/DC Coverage from its tile or Noyce Compliance: Open MC/DC Coverage. It has three tabs: Decisions, Measured coverage and Review uncovered.

What it needs#

clang, llvm-nm (or nm), llvm-profdata and llvm-cov, LLVM 18 or newer, so that clang accepts -fcoverage-mcdc. Noyce IDE checks this by compiling a test file. Override the tools with NOYCE_COV_CC, NOYCE_COV_NM, NOYCE_COV_PROFDATA and NOYCE_COV_COV.

With only GCC and gcov, Measure module is disabled with "This toolchain cannot measure MC/DC", and no coverage is measured. No statement or branch figure is shown in place of MC/DC.

Measure a module#

  1. Write a test driver with a main() under tests/mcdc/ that exercises one source file, and name that file in a comment: // @coverage-source ../../src/my_module.c. Add // @coverage-extra-source <file> for other files to link and // @coverage-include <dir> for include directories.
  2. In Measured coverage, pick the Module; the Driver follows it. Select Measure module. The module is built with LLVM's coverage and MC/DC instrumentation, the driver runs, and the result is read back. A run is a background job you can Cancel, limited to five minutes by default.
  3. Each record shows its environment, tool, MC/DC form and status. Reread results reads the records again.

Vendor headers and functions the module needs but the host does not have are generated as stubs that return 0. The record lists every stubbed symbol, because a branch decided by a stub was decided by the stub, not by your code. The record is marked Host, stubbed, and its caveat says DO-178C 6.4.1 requires the differences between this environment and the target to be analysed before it counts as verification credit.

noyce cover --host runs every driver in tests/mcdc/ and writes .noyce/coverage/<driver>.json and the merged mcdc.json.

MC/DC form#

Both unique-cause and masking MC/DC are measured. Choose the form with the setting noyce.coverage.mcdcForm (unique-cause by default, or masking); it is recorded on every coverage record and must match what your PSAC and SVP state.

How results combine#

  • A re-run of the same driver, module, environment and tool replaces the previous record.
  • Records of different drivers for the same module are combined by their condition vectors, so an independence pair split across two drivers counts.
  • Different environments or tools are not combined in the dashboard figure: each module counts the newest environment's records.
  • A record measured on a different version of the source is excluded and listed as stale; measure the module again.
  • A module that has not been measured counts its obligations with no coverage, marked "a structural zero, not a result".

Target coverage probes#

For coverage on the target with your own toolchain, the noyce-core engine can instrument the sources: a statement probe at each basic block, and decision and condition probes that keep short-circuit evaluation. Instrumented copies go to .noyce/cov/build/<config>/, with a small runtime (noyce_cov.c, no heap, no C library) and a probe map; your sources are never edited. A statement-only mode is available for small parts, and an RTT streaming mode. Collected counter RAM becomes .noyce/coverage/cov-probe-<config>-<host|target>.json, tagged Measured, and appears in Measured coverage with tool "Noyce probes" and its chip, probe and MC/DC form.

Target verification#

MC/DC Coverage → Measured and Unit tests → On target have a Target verification section. It reads "Not verified on hardware — connect a probe" until a probe has produced a record.

  • Build instrumented image instruments the project's own C sources (vendor trees, SDK paths, system_*.c and SEGGER RTT are left out, with the reason), stages them as overlay slots and builds the firmware with the portable build and your cross toolchain. The image, its link map, the probe map and image.json (the image hash) go to .noyce/cov/build/target/. No probe is needed.
  • Flash & run takes the image last built (refusing one whose hash changed, or built for other tests), attaches, flashes with read-back verification, runs, halts and reads the counters.
  • Build, flash & collect does both in one go.

With target tests in tests/target/ the image runs them to their END line over RTT, masks interrupts, and is halted; without, the application runs for 5 seconds and is halted. Generated unit drivers copied there from Unit tests are compiled in place of their unit, so each unit is linked once. Tick Coupling probes to build .noyce/cov/build/coupling/target.elf instead, the image Data & Control Coupling's Collect from target reads.

The steps show live: Detect probe, Read build and chip, Instrument sources, Build instrumented image, Attach, Flash and verify, Run, Halt, Read counters, Detach, Write records. The first one that fails stops the run and is named; the probe is always released. The counters are only ever read from the target's RAM; before reading, the image on disk is hashed again and must still be the one flashed, and the collected record must name that image and build. The run record (.noyce/verification/target-verify/runs/<id>.json) carries the chip, probe and serial, image hash, toolchain, the RTT text's hash and the coverage totals; the target tests' verdicts also go to Test Explorer's Run on target records.

The chip comes from the Chip field, else the CubeMX .ioc (Mcu.UserName, e.g. STM32G431VBTx), else the build's MCU. The same flow runs headless as noyce verify --target (CLI).

Limitation

  • The flow is built and tested against a fake device and with real cross-compiles, but it has not been run on hardware. Do not rely on target probe coverage until a first board run has produced a record.
  • A TI CCS project (Canister, TM4C1294) has no GNU ld linker script, so the portable build cannot link an image and the flow stops at Read build and chip.
  • noyce cover --target <probe> --config <id> (--dumps … | --elf …) still collects from an image you built, flashed and ran yourself.

Object-code branch coverage#

Open Object Code Traceability (Noyce Compliance: Open Object Code Traceability). It has three tabs: Untraceable runs, Object branches and Execution targets.

Capture the disassembly#

Build the firmware with -g, choose the image, then select Capture disassembly. Noyce IDE runs arm-none-eabi-objdump (or llvm-objdump, or objdump) on the linked image and analyses it in the view; nothing outside the app is needed. It looks on PATH and in the Arm toolchain set in noyce.stm32.armToolchainPath or noyce.stm32.cubeIdePath. Results are written to .noyce/socta/. An image with no DWARF line table is "Not analysed".

Untraceable runs lists object code no source line accounts for, each needing a justification. At Level A a justification by one person shows Not independent.

Import an execution trace#

Object branches lists every conditional branch in the image, mapped to a source decision where there is one. A branch with no source decision (compiler-generated code such as switch tables or division helpers) must be covered or justified. Until a trace is imported the tab reads Not measured: branch outcomes are unknown, not zero.

Run the image yourself, then select Import trace…. Accepted formats:

  • QEMU -d exec,nochain log, or the QEMU execlog plugin output;
  • Renode ExecutionTracer output (PC, PCAndOpcode or Disassembly; opcode-only is refused);
  • an address list decoded from ETM or MTB trace, which must say which. ETM and MTB decoding is not done in Noyce IDE.

The trace is copied to .noyce/objcov/traces/. A trace taken from a different build of the image is not joined.

Execution targets#

Execution targets lists what can run the image here: hardware through probe-rs, QEMU and Renode, and whether each was found. Simulator support by part is taken from the simulators' documentation, marked Not verified:

  • STM32G431 (the H-Bridge controller): no STM32G4 machine in QEMU, and no STM32G4 platform confirmed in Renode. Object coverage needs ETM trace from the target, if the part has it fitted, or a core-only QEMU board for portable code.
  • TM4C1294 (the Canister controller): no Tiva C machine in QEMU (lm3s6965evb is a different part) and none confirmed in Renode. Use hardware trace.

Limitation

No real execution trace has been ingested yet; only synthetic fixtures were tested, and a fixture trace is marked "it is a fixture and will not count as evidence". There is no button to run QEMU or Renode from the view, although the Not measured notice suggests running them: run the simulator yourself and import its trace.

Coverage review#

The Review uncovered tab of MC/DC Coverage lists every obligation left uncovered by measured runs, and asks a person to classify each one:

Classification Effect
Missing test case Drafts a verification case for the requirement you name. The item stays open until a test covers it.
Dead code Raises a problem report. The item stays open: dead code is removed, not justified away.
Deactivated code Closes the item. Needs the mechanism (configuration or design), a reference, and how execution is prevented.
Justified Closes the item, with the analysis.

Signing. Choose who signs under Signed by, a person on the roster (an AI never counts). Closing classifications need the verifier role. At Levels A and B the signer must be independent of the code's authors, which are read from the file's git history. If the file has no git history, an Independent reviewer with the verifier or SQA role co-signs. Select Sign classification; the record is written to the audit trail.

Records are append-only, one file each under .noyce/process/coverage-classifications/. A record stops counting, and shows Reclassify, when the source changed since it was signed, the record was altered, or the signer left the roster.

Obligations that cannot be proven either way, for example a macro decision whose MC/DC LLVM did not report, show "Measure again before classifying" and cannot be classified.

The review counts an obligation as covered if any record from the same tool covered it, in any environment; the dashboard figure counts only each module's newest environment. The two can therefore differ.

Limitations#

  • Host coverage needs LLVM/Clang 18 or newer; there is no gcov path.
  • Host records are stubbed; DO-178C 6.4.1 environment analysis is yours to do.
  • Target probe coverage is unverified on hardware; the flow has been tested against a fake device only.
  • Object-code coverage has been tested with synthetic traces only. QEMU and Renode do not model STM32G431 or TM4C1294; ETM or MTB traces must be decoded outside Noyce IDE.
  • Known engine problems are listed in qualification/known-problems/ (cov-host.md, cov-probe.md, object-coverage.md); for example, LLVM's summary reports 0/0 MC/DC for decisions inside macros although its detail is correct.
