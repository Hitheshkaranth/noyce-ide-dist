Build, test & debug

Building TI projects in the IDE, running unit and target tests, the AI build-repair loop, STM32 workspace setup, probes and RTT, and following an agent's work in Agent Output.

Build Pipeline#

Builds a TI Code Composer Studio project with the TI compiler you have installed, without opening CCS. Open it from the Build Pipeline tile or Noyce Build: Open Build Pipeline.

What it can build. A project with a CCS .cproject at its root. It reads the configuration, the declared compiler (TI ARM CGT armcl, TI Arm Clang tiarmclang or GNU Arm arm-none-eabi-gcc), the sources and the include paths.

How it finds the compiler. Your PATH first, then the TI install folders: ~/ti and /Applications/ti on macOS, C:\ti and %USERPROFILE%\ti on Windows. When several versions are installed, the newest is used. TivaWare is found automatically; other SDK locations come from the COM_TI_*_INSTALL_DIR and SW_ROOT environment variables.

Running a build

  1. Read the Build (TI CCS) stage. Before a run it shows the project, the compiler found, any unresolved variables, the include paths and the exact command line. If anything is missing the stage reads blocked and says what.
  2. Select Build with compiler. The build runs for up to 15 minutes.
  3. The stage shows Passed or Failed, the duration, the full compiler output and the exit status.

Output never goes into your project's own Debug/ folder. Object files, and the .out and .map when the project links, are written to .noyce/build/ccs-<configuration>/, together with a build-record.json of the compiler, command, exit code and output. The IDE only runs compilers it found itself.

Note

Linking happens only with armcl and a linker command file whose libraries all resolve; otherwise the build compiles only. The YAML Source tab is generated from the stage names for reference; it is not a pipeline file in your project. Artifacts lists log lines that mention build outputs.

Test Explorer#

Finds the project's C unit tests, runs them on your computer, and runs requirement-based tests on the target through a debug probe. Open it with ⌘⌥N then T.

Unit tests on your computer

  • Tests are found by scanning .c and .cpp files for TEST_CASE( or void test_… functions; each file is a suite.
  • Run All compiles every test file, with Unity, into one program using your host gcc, runs it, and shows each test's result. If the project does not include Unity, the IDE's bundled copy is used from .noyce/unity/. It needs gcc and gcov on macOS or Linux.
  • AI Generate has the Test Engineer agent write Unity tests for the active file, compiles and runs them, and makes one repair attempt if they fail. The generated tests are staged as a change set, not written into your project.

Important

Run All results are shown in the panel only; they are not recorded as verification evidence. Use By requirement → Run tests for a recorded run.

Requirement-based tests. Switch the right pane to By requirement and select Run tests. Noyce IDE runs your project's own test command (make test, or make in tests/ or test/) and seals the result under .noyce/verification/test-runs/.

Run on target. Builds tests/target/*.c with the portable build, flashes it through a probe-rs probe (ST-Link, J-Link or CMSIS-DAP), verifies the flash, and reads TEST name reqs PASS|FAIL lines over RTT. Each run is recorded with the chip, probe, firmware SHA-256 and toolchain in .noyce/verification/target/runs/. It needs:

  • an attached probe,
  • portable-build/build-config.json with a linker script (select Generate portable build in Evidence Records → Change sets),
  • at least one tests/target/<name>.c defining noyce_suite_<name>(), and a main() in the build.

Nothing is recorded unless flashing finished and read back correctly.

Firmware Validation Loop#

Builds, flashes and checks your firmware with your own commands and, when a step fails, asks the coding agent for a repair. Open it with ⌘⌥N then V; Noyce: Configure Firmware Validation Loop opens its settings.

Setting Default
noyce.agents.firmwareLoop.buildCommand none Required. Any shell command, run in the workspace folder.
noyce.agents.firmwareLoop.flashCommand none Optional.
noyce.agents.firmwareLoop.observeCommand none Optional, for example reading the serial port.
noyce.agents.firmwareLoop.successPattern none Regular expression the observe output must match.
noyce.agents.firmwareLoop.timeoutSeconds 120 Per command, 5 to 600.
noyce.agents.firmwareLoop.autoApply off Skips the review prompt; the repair is still only staged.

One run: build, then flash, then observe. A step fails on a non-zero exit, a timeout, or an observe output that does not match the pattern. On the first failure the coding agent receives the command, its output and the source files it names, and returns a patch. You review it and Stage for Review; it becomes a change set. It is never written to your files directly.

Note

In v2.0.7 the loop stops after the first repair is staged. Approve and apply the change set in Evidence Records, then run the loop again. The loop needs noyce.agents.enableShell; it asks before turning it on.

Fix Build Errors with AI is the single-pass version: it takes the errors in the Problems panel (no build is run), asks the coding agent for fixes, and stages them as a change set with Stage all fixes or Stage per file….

STM32 projects#

Command Does
Noyce STM32: Import CubeIDE Project Reads a .ioc or project folder and writes .vscode/tasks.json, launch.json, settings.json, extensions.json and compile_commands.json: a make build task, an OpenOCD flash task, a Cortex-Debug launch configuration, and clangd set up for the project. It also loads the pin configuration. Existing files of those names are overwritten.
Regenerate Workspace Files Writes the same files again for the open folder.
Validate Toolchain Checks arm-none-eabi-gcc, arm-none-eabi-gdb, openocd (required), make, cmake, STM32_Programmer_CLI and st-util on your PATH, one line each.
List Debug Probes Lists connected probes through probe-rs.
Read Target Memory, Start / Stop RTT Streaming Read memory and stream RTT into the "Noyce RTT" output.

Limitation

In v2.0.7, Read Target Memory, RTT streaming and the STM32 Debug State view's registers and memory watches need a probe already attached, and these STM32 commands have no attach step of their own, so they report "No debug target attached" or stay empty. Use the Debug Probe view to attach, flash and read memory instead.

Agent Output#

Follow what each Orchestrator agent is doing and what it produced. Open it with Agent output in the Orchestrator.

  • One tab per agent, with a dot while it is running or waiting for your review, and its task count. The view follows the agent currently running.
  • Workflow Tasks on the left: the tasks routed to that agent and their status.
  • The selected task: the live output as it streams, Model reasoning (opens on its own while the model is thinking), Actions (each tool step, with steps that write files or run commands marked apart), and a Run summary with the outcome, tokens and time.
  • Proposed file changes for the coding and test agents, with Stage all as change set or Stage per file. Nothing is written until the change set is approved and applied.

Limitation

In v2.0.7 the Trace agent's tab shows a "Coverage Analytics Updated" card with fixed figures (100% traced, 96% covered) that are not measured. Use the Compliance Dashboard and MC/DC Coverage for real numbers.
