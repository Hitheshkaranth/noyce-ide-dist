Build, test & debug

Building TI projects with ⇧⌘B and the Build view, running unit and target tests, the AI build-repair loop, STM32 workspace setup, probes and RTT, and following an agent's work in Agent Output.

Build#

Noyce IDE builds a TI Code Composer Studio project with the TI compiler you have installed, without opening CCS. You can build the way you would in any other IDE, from a task and the status bar, or from the Build view, which shows the result in detail.

What it can build. A project with a CCS .cproject at its root. Noyce IDE reads its build configurations, the declared compiler (TI ARM CGT armcl, TI Arm Clang tiarmclang or GNU Arm arm-none-eabi-gcc), the sources and the include paths. The Build view also builds STM32CubeIDE projects with a .cproject at the root or one folder down.

How it finds the compiler. Your PATH first, then the TI install folders: ~/ti and /Applications/ti on macOS, C:\ti and %USERPROFILE%\ti on Windows. When several versions are installed, the newest is used. TivaWare is found automatically; other SDK locations come from the COM_TI_*_INSTALL_DIR and SW_ROOT environment variables. The IDE only runs compilers it found itself.

Build from the keyboard#

When the open folder has a CCS project, two items appear on the left of the status bar: the build configuration (for example Debug) and Build.

To Do
Build the selected configuration ⇧⌘B (CtrlShiftB on Windows), Build in the status bar, or Noyce Build: Build.
Choose the configuration Select it in the status bar, or Noyce Build: Select Configuration.
Delete this configuration's build output Noyce Build: Clean.
Run a specific configuration Tasks: Run Task → Noyce Build → Noyce: Build Debug, Noyce: Build Release or Noyce: Clean ….

The build runs as a task in the terminal panel, so the compiler output streams as it is produced and you can stop it like any other task. The status bar item then reads Built with the duration, Build failed with the error count, or Build cancelled.

Compiler errors and warnings go to the Problems panel and are underlined in the editor. TI armcl diagnostics ("file.c", line 145: warning #994-D: …), fatal errors and remarks each have their own problem matcher; GNU builds use the standard $gcc matcher.

The Build view#

Open it from the Build Pipeline tile, Noyce Build: Open Build Pipeline or ⌘⌥N then B.

  • Header: the project, the compiler found and its version, the last result, and Build. When something is missing, Build is disabled and a Build blocked panel lists each problem: the compiler, CG_TOOL_ROOT, or an SDK path that did not resolve.
  • Configuration: the CCS build configuration to build.
  • Errors, Warnings, Duration and Image size. Image size comes from the link map; Open Firmware Memory opens the full breakdown.
  • Diagnostics: every error, warning and remark with its code. Select the file and line to open it. Diagnostics in vendor SDK files are marked vendor and listed after your own.
  • Output: the full compiler output.
  • Toolchain: the compiler path and version, the exact build command, its working directory, and the SDK variables used.
  • Artifacts: the files the build wrote, with size and modified time.
  • History: the latest stored CCS build of each configuration, with its result and duration. Every build is listed in the sidebar Build Status view (below).

Where the output goes#

Output never goes into your project's own Debug/ or Release/ folder. Object files, and the .out and .map when the project links, are written to .noyce/build/ccs-<configuration>/, together with a build-record.json of the compiler, command, exit code, duration and output. The task, the status bar and the Build view all read and write the same record, so a build started from the keyboard shows up in the Build view's history. Firmware Memory reads the .map from there.

An STM32CubeIDE build from the Build view runs make all in the configuration's own output folder, as CubeIDE does, and writes its record to .noyce/build/stm32-<configuration>/build-record.json (toolchain, command, exit code, duration and output). A build that make never started, for example because make is not installed, is not recorded.

Before it runs, the Build view checks that the CubeIDE makefiles only name paths that exist on this computer. Makefiles generated on another machine (a C:/… path on a Mac, for example) block the build. The Build blocked panel then offers Build with a generated makefile: Noyce IDE writes its own makefile from the .cproject and .ioc under .noyce/build/stm32-<configuration>/portable-build/ and builds with arm-none-eabi-gcc and make. It is not the CubeIDE build. When a compiler without its C library stops the build, the output starts with a hint naming the fix. When a build fails before reporting any error against a file and line, the Errors tile says so. A walkthrough of both paths is in Import and build.

Which compiler. Set noyce.stm32.armToolchainPath to a toolchain's bin folder to choose the compiler. A tool in that folder wins over one on PATH: in Validate Toolchain, in the generated tasks (the folder goes first on their PATH), in the debug launch and in the Build view (passed to the generated makefile as GCC_PATH). Otherwise PATH is used, then STM32CubeIDE's bundled tools. The record keeps the compiler's measured version.

The STM32 ⇧⌘B task that Regenerate Workspace Files writes is recorded the same way, with the compiler version it measured. Its output stays in the terminal and is not stored in the record.

Each build-record.json holds only the latest build of its configuration. Every recorded build, CCS or STM32, also adds one line to .noyce/build/history.jsonl with its time, kind, project, configuration, exit code, duration and toolchain. The file keeps the last 200 builds. The sidebar Build Status view lists the newest 10, with the result, CCS or STM32, the duration and how long ago; hover one for the toolchain and exit code, or select it to open the Build view. A project built before history.jsonl existed shows the latest build of each configuration until its next build.

Note

Linking happens only with armcl and a linker command file whose libraries all resolve; otherwise the build compiles only, and there is no .map or image size.

Your own build tasks#

The Noyce build tasks have the task type noyce-ccs, so you can add your own to .vscode/tasks.json, for example to bind a Release build to a key:

json
{
  "version": "2.0.0",
  "tasks": [
    {
      "type": "noyce-ccs",
      "configuration": "Release",
      "action": "build",
      "label": "Noyce: Build Release",
      "problemMatcher": ["$ti-armcl"]
    }
  ]
}

configuration is the CCS configuration name and action is build or clean.

Test Explorer#

Finds the project's C unit tests, runs them on your computer, and runs requirement-based tests on the target through a debug probe. Open it with ⌘⌥N then T.

Unit tests on your computer

  • Tests are found by scanning .c and .cpp files for TEST_CASE( or void test_… functions; each file is a suite.
  • Run All compiles every test file, with Unity, into one program using your host gcc, runs it, and shows each test's result. If the project does not include Unity, the IDE's bundled copy is used from .noyce/unity/. It needs gcc and gcov on macOS or Linux.
  • AI Generate has the Test Engineer agent write Unity tests for the active file, compiles and runs them, and makes one repair attempt if they fail. The generated tests are staged as a change set, not written into your project.

Every Run All is recorded under .noyce/verification/test-runs/ with its run id.

Requirement-based tests. Switch the right pane to By requirement and select Run tests. Noyce IDE runs your project's own test command (make test, or make in tests/ or test/) and seals the result under .noyce/verification/test-runs/.

Run on target. Builds tests/target/*.c with the portable build, flashes it through a probe-rs probe (ST-Link, J-Link or CMSIS-DAP), verifies the flash, and reads TEST name reqs PASS|FAIL lines over RTT. Each run is recorded with the chip, probe, firmware SHA-256 and toolchain in .noyce/verification/target/runs/. It needs:

  • an attached probe,
  • portable-build/build-config.json with a linker script (select Generate portable build in Evidence Records → Change sets),
  • at least one tests/target/<name>.c defining noyce_suite_<name>(), and a main() in the build.

Nothing is recorded unless flashing finished and read back correctly.

Firmware Validation Loop#

Builds, flashes and checks your firmware with your own commands and, when a step fails, asks the coding agent for a repair. Open it with ⌘⌥N then V; Noyce Agents: Configure Firmware Validation Loop opens its settings.

Setting Default
noyce.agents.firmwareLoop.buildCommand none Required. Any shell command, run in the workspace folder.
noyce.agents.firmwareLoop.flashCommand none Optional.
noyce.agents.firmwareLoop.observeCommand none Optional, for example reading the serial port.
noyce.agents.firmwareLoop.successPattern none Regular expression the observe output must match.
noyce.agents.firmwareLoop.timeoutSeconds 120 Per command, 5 to 600.
noyce.agents.firmwareLoop.autoApply off Skips the review prompt; the repair is still only staged.

One run: build, then flash, then observe. A step fails on a non-zero exit, a timeout, or an observe output that does not match the pattern. On the first failure the coding agent receives the command, its output and the source files it names, and returns a patch. You review it and Stage for Review; it becomes a change set. It is never written to your files directly.

Repairs iterate up to maxAttempts times in an isolated copy under .noyce/firmware-loop/trial, rebuilding there after each patch. One change set with the combined repair is staged, with how many attempts were made and whether the trial build passed. Flash and observe run only on your real workspace.

Note

The loop needs noyce.agents.enableShell; it asks before turning it on.

Fix Build Errors with AI is the single-pass version: it takes the errors in the Problems panel (no build is run), asks the coding agent for fixes, and stages them as a change set with Stage all fixes or Stage per file….

STM32 projects#

Command Does
Noyce STM32: Import CubeIDE Project Reads a .ioc or project folder and writes .vscode/tasks.json, launch.json, settings.json, extensions.json and compile_commands.json: a make build task, an OpenOCD flash task, a Cortex-Debug launch configuration, and clangd set up for the project. It also loads the pin configuration. Existing files of those names are overwritten.
Regenerate Workspace Files Writes the same files again for the open folder.
Validate Toolchain Checks arm-none-eabi-gcc, arm-none-eabi-gdb, openocd (required), make, cmake, STM32_Programmer_CLI and st-util, one line each, then says whether you can build, flash and debug and why not. A compiler without its C library (newlib) is reported as blocking the build.
List Debug Probes Lists connected probes through probe-rs.
Attach Debug Probe, Detach Debug Probe Attach to the target through probe-rs; the status bar shows the attached target.
Read Target Memory, Start / Stop RTT Streaming Read memory and stream RTT into the "Noyce RTT" output.

Memory reads, RTT and the STM32 Debug State view offer to attach when no probe is attached yet. Memory watches are kept across reloads.

Agent Output#

Follow what each Orchestrator agent is doing and what it produced. Open it with Agent output in the Orchestrator.

  • One tab per agent, with a dot while it is running or waiting for your review, and its task count. The view follows the agent currently running.
  • Workflow Tasks on the left: the tasks routed to that agent and their status.
  • The selected task: the live output as it streams, Model reasoning (opens on its own while the model is thinking), Actions (each tool step, with steps that write files or run commands marked apart), and a Run summary with the outcome, tokens and time.
  • Proposed file changes for the coding and test agents, with Stage all as change set or Stage per file. Nothing is written until the change set is approved and applied.
  • The Trace agent's tab shows the project's linked-requirement ratio and measured MC/DC, or "Not measured".
