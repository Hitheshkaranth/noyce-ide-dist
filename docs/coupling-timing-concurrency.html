Coupling, timing and interrupt analysis

Data and control coupling measured by instrumented requirements-based test runs (A-7(8)), execution time and stack depth measured on the target with static comparison (A-5(6), A-6(5)), and the analysis of data shared between interrupts and thread code.

Data & Control Coupling#

DO-178C A-7(8) asks that tests exercise the data and control coupling between components. Noyce IDE enumerates every coupling from the program model, measures which ones a requirements-based test run actually exercised, and lets a rostered person justify the rest. Open it with Noyce Compliance: Open Data & Control Coupling or the DC/CC analysis tile.

What is a coupling. A data coupling is a writer in one component, a variable, and a reader in another. A control coupling is a call from one component into another, including calls through function pointers, whose candidate targets are the address-taken functions of a matching type.

Use it#

  1. Analyze coupling parses the project's own sources and enumerates every coupling between components. Vendor trees are out of scope. The result is written to .noyce/coupling/static.json.
  2. Measure coupling (host) builds each host test driver twice, plainly and with coupling probes, runs it case by case, and collects which couplings each test exercised. Drivers are tests/**/test_*.c files that carry the same @coverage-source comments as MC/DC drivers. Results go to .noyce/coupling/measured-*.json, and test results are appended to .noyce/verification/results.jsonl.
  3. Review the table. The default filter is Open; others are Not measurable, Satisfied and All.

Both jobs run in the background with Cancel. Analyze is limited to 10 minutes, Measure to 20.

When a coupling counts#

A coupling is Satisfied only when a test run exercised it and that run is requirements-based: a verification case in Evidence Records → Verification cases names the test, verifies at least one requirement, and its latest result is a pass with an execution record. Requirement ids are never guessed from test names. A coupling exercised only by other tests reads Not by a requirements test.

A coupling no test exercised can be Justified: a reason, an author on the roster, and at Levels A and B a reviewer who is a different person on the roster. Justifications are stored in .noyce/coupling/justifications.json.

Unresolved accesses (pointer accesses, escaped addresses and pointer calls the analysis could not resolve) are listed separately and must each be justified.

The objective is satisfied only when nothing blocks it. What keeps A-7(8) open lists the blockers: not analyzed, not measured, couplings not exercised, couplings outside the measured build, no requirements-based runs, unjustified unresolved accesses, or a component map nobody has reviewed.

The component map#

Which source files make up each component comes from the SDD's component table (columns Component and Source Files). Without one, each source file is its own component, and the view says this is a default, not the design. The map is stored in .noyce/coupling/components.json. Choose a reviewer on the roster and select Record review; editing the map afterwards makes the review stale. The map can only be edited by hand in that file.

Level#

The view uses the software level recorded in Compliance. If none is recorded it assumes Level A and shows "(assumed)". noyce couple refuses to assume a level.

Limitation

  • Collect from target (probe) reads .noyce/cov/build/coupling/target.elf. Build it with Coupling probes ticked in Target verification (or noyce verify --target --coupling), which also flashes, runs and collects in one go. Target coupling collection is unverified on hardware.
  • A test driver whose instrumented run behaves differently from its plain run is dropped from the measurement without a notice in the view.
  • The Compliance Dashboard and the life-cycle documents still use the older name-matching estimate when no measured report exists; that estimate is marked heuristic and cannot close A-7(8).

Known engine problems, such as memcpy counting as a whole-object access and interrupt and thread probes not being serialised, are listed in qualification/known-problems/coupling.md.

Timing & Stack#

Execution time and stack depth measured on the target, compared with the static worst-case stack. Open it with Noyce Compliance: Open Timing & Stack. Every measured figure is labelled "measured — not a bound": a measurement shows what happened in that run, never a worst case.

Use it#

With unit drivers in tests/target/, noyce verify --target --timing does steps 1 to 4 in one go: one timing site per driver, the runtime compiled into the verification image, collected after coverage.

  1. Select Prepare runtime. It writes the timing runtime to .noyce/timing/build/<config>/. Add those sources to your build, compile with -DNOYCE_TIMING -DNOYCE_TIMING_HAS_CONFIG -I <dir>, and link with the -Wl,--wrap=… options the notice lists for interrupt handlers.
  2. Call noyce_timing_init() and noyce_stack_paint() first in main.
  3. Flash and run the firmware, attach the debug probe in the Debug Probe view, and halt the target.
  4. Select Collect from target. Results go to .noyce/timing/timing-<config>-target.json.

Set Core clock to see microseconds; it is read from the project's CubeMX .ioc file when there is exactly one, otherwise type it. Without a clock, times stay in cycles. Config names the build.

How it measures. Time uses the DWT cycle counter around each timed site. Cortex-M0, M0+ and M23 have no cycle counter, so time is Not measured there. Stack depth comes from painting the stack with a pattern and reading the high-water mark; painting needs CMSIS (__StackLimit / __StackTop) or STM32Cube (_estack, _Min_Stack_Size) symbols in the linker script. Interrupt handlers are timed only, not painted. Durations above 2^32 cycles wrap without detection. Per-call figures come from the unit test drivers built with -DNOYCE_TIMING.

Static worst case walks the program model's call edges with the compiler's .su stack-usage files, so build with -fstack-usage and build the program model (Build program model). It reports main plus every handler nested at once; NVIC priorities would lower that. The walk does not follow function-pointer calls.

WCET. Noyce IDE does not compute worst-case execution time. Import WCET report… reads bounds from an external analyser (noyce.wcet/1 JSON, or CSV with function and wcet_cycles or wcet_us columns) and compares measurements with them: "Within bound" is consistent, never a confirmation.

Limitation

  • On-target collection (cycle counter, stack painting, probe-rs reads) has not been verified on hardware.
  • A static stack figure reads Complete even when the code calls through function pointers; those calls are listed only in the warnings and are not counted.
  • The runtime wraps every handler the static walk recognises by name, including reset and fault handlers. Check the wrap list before you build.

Interrupt & Shared Data#

Finds every interrupt service routine and every global accessed from both interrupt and thread context, and flags accesses that can be torn or lost. Open it with Noyce Compliance: Open Interrupt & Shared Data, or run it with noyce analyze. Results are Derived and stored in .noyce/analysis/concurrency/result.json.

Analyze builds the program model, then analyses it; Re-run without rebuilding model skips the build.

Interrupts are found from C vector-table initialisers, assembly vector tables, interrupt attributes and vendor keywords, and run-time registration calls such as IntRegister. A handler found only by its name is listed as unconfirmed and not analysed as an ISR. Thread context is main, the reset handler, and RTOS task entries (FreeRTOS xTaskCreate, CMSIS-RTOS osThreadNew, ThreadX tx_thread_create).

Findings: non-atomic read-modify-write, multi-word access, a function that runs in both contexts, missing volatile, and unprotected write/write. Each is Definite or Possible, with the reason when it is only possible (for example protected on some paths only, or the interrupt was found only by registration). Accesses inside a recognised critical section (__disable_irq/__enable_irq, IntMasterDisable/Enable, BASEPRI and PRIMASK writes, FreeRTOS and CMSIS-RTOS critical sections, __HAL_LOCK), or made before interrupts are enabled, are listed as suppressed with what protected them.

The results support DO-178C A-5(6); "Analysis, not a review; these results support A-5.6 and cannot satisfy it alone."

Note

  • All RTOS tasks are treated as one thread context, so task-against-task races are not reported, and nested interrupt priorities are not modelled, so interrupt-against-interrupt races are not reported.
  • The critical-section, interrupt-enable and task-creation lists are built in; there is no project file to change them in this release.
  • Pointer aliasing is not resolved; unresolved pointer accesses are listed for review.
  • Functions reachable only through unresolved function pointers are in no context.

Limitations#

  • Target coupling collection is built and tested against a fake device only; it is unverified on hardware.
  • Timing and stack collection on the target is unverified on hardware; no static WCET is computed.
  • The interrupt analysis's configuration lists are not user-configurable.
